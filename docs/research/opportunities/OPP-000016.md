# OPP-000016: FFT-based fast path for full-mode np.correlate / np.convolve

Source: numpy/numpy#1858, "Use FFT in np.correlate/convolve? (Trac #1260)",
migrated to GitHub by thouis on 2012-10-19, mirroring an original trac
ticket opened by user "roger" on 2009-10-12. State at ingestion: open.
Labels: `01 - Enhancement`, `component: numpy._core`.

## What is slow

`np.correlate` and `np.convolve` compute full-mode (all-lags) results using
NumPy's direct, naive summation implementation, roughly O(n*m) work. The
reporter measured MATLAB's `xcorr(randn(1e6,1))` completing in about 0.35s,
while `x = randn(1e6); correlate(x, x)` in Python "takes more than a minute
(then killed)"; also "MATLAB is also much faster for arrays of 1e5
elements" (no exact number given), and `fftconvolve` in `scipy.signal` was
"even slower" at the time. josef-pkt later clarifies the actual slow
regime: default (`mode='valid'`) `correlate(x,x)` "takes no time since it
only calculates one value," but `np.correlate(x,x,'full')` "is also taking
around an hour" at 1e6 - the complaint is specifically full-mode, all-lags
convolution/correlation on large arrays.

## Why (per the thread)

The root cause is algorithmic, not platform-specific: MATLAB's `xcorr` is
reportedly fast because it uses FFT internally (per josef-pkt, 2009-10-16:
"xcorr in matlab signal toolbox seems to use fft"), while naive direct convolution is slow
regardless of language. josef-pkt proves this by timing MATLAB's own plain
`conv()` on the same 1e6-element data: "also takes forever (around or close
to an hour)." The gap is not "MATLAB beats NumPy," it is "FFT-based
convolution beats naive convolution," and `correlate`/`convolve` had no
FFT-based code path to switch to. pv notes scipy's `fftconvolve` had a
separate, unrelated slowness bug at the time (non-power-of-two FFT sizes).

## Who reported and when

Original trac ticket #1260 opened 2009-10-12 by trac user "roger", migrated
to GitHub as numpy/numpy#1858 by thouis on 2012-10-19. Discussion runs
2009-10-13 through 2011-02-18; no comments recorded after that. Open more

## Maintainer objections

cournape (2009-11-25): "FFT has several disadvantages: it does not work for
object arrays, can be memory hungry, and slower when only a few values of
the correlation is needed. I think we should keep the current implementation
based on naive implementation, and add a FFT-based one. The current function
could take an argument to force naive, fft or heuristic (to try to pick the
fastest one)."

pv (2009-10-16): "I don't think there is any significant disadvantage in
using FFT. It might be a bit slower for small N than explicit convolution,
and might for intermediate N introduce more numerical error (we're talking
maybe about 1e-11 or so). IIRC, for large N FFT should be better both for
the numerical error and performance. I don't believe you can perform FFT
convolution with integers using the tools currently in Numpy -- cast to
complex is probably always needed."

Neither opposes an FFT path outright; both list conditions to handle, and
cournape's own naive/fft/heuristic dispatch matches the shape below.

## Existing projects / PRs that attempted it

No numpy-internal PR is linked here that directly adds an FFT path to
`correlate`/`convolve`. Cross-referenced: **scipy/scipy#337** and
**scipy/scipy#2651** ("Fold fftconvolve into convolve/correlate functions
as a parameter", closed) - the latter the scipy-side version of this ask,
echoing endolith's suggested `fft=True` option (as the now-removed STSCI
`correlate2d`/`convolve2d` once had). **numpy/numpy#5954** and
**numpy/numpy#5978** ("adding maxlag mode", closed) mitigate the same pain
differently: fewer lags, not faster lags. **numpy/numpy#22255** ("Fourier
transform option for numpy.polynomial.polymul", closed) lands FFT on a
different function. **bids-standard/pybids#411** (closed) shows a
downstream project building its own convolution fix instead. None confirm
a merged numpy-side FFT path for `correlate`/`convolve`; the dump shows no
status past "closed" for any of them.

## What semantics differ

An FFT path changes results three ways: (1) output becomes approximate,
"1e-11 or so" relative error per pv, worse at intermediate N and better
than naive at large N; (2) integer inputs need an internal cast to
complex/float, since per pv you cannot "perform FFT convolution with
integers using the tools currently in Numpy" without it; (3) object-dtype
arrays cannot use FFT at all (per cournape) and must fall back to naive.
cournape also flags FFT as "memory hungry" and "slower when only a few
values of the correlation is needed," so `mode='valid'` single-lag calls
(already fast per josef-pkt) must stay off the FFT path.

## Is it common enough to matter

Plausibly yes: josef-pkt independently uses `np.correlate` in finance
time-series work at "a few hundred to 10000" observations, sometimes on
integer data for "bias correction" - smaller-N than the original
1e6-element complaint. **bids-standard/pybids#411** shows a downstream
neuroimaging project built its own convolution fix rather than rely on
numpy/scipy. Against that: the issue stayed open 15+ years with maintainer
engagement confined to 2009-2011 and no comments since, and
`scipy.signal.fftconvolve` has existed as a workaround, which may have
reduced pressure on numpy itself.

## What PyOverdrive should do next

1. Write the Dyno reproducer: baseline `np.correlate(a, a, mode='full')`
   and `np.convolve(a, a, mode='full')` against a candidate FFT-based
   convolution (`numpy.fft.rfft`/`irfft`), sweeping sizes
   `[1_000, 10_000, 100_000, 1_000_000]` and dtypes `float64`/`int64` (int64
   cast through complex, per pv), to replace the 171.4x lower bound here.
2. If a clean crossover size N* emerges where FFT wins on `mode='full'`/
   `'same'` for same-dtype, non-object 1-D real arrays, that is the
   transparent fast-path shape: dispatch on array length alone, matching
   cournape's own "force naive, fft or heuristic" proposal.
3. Measure numerical error against pv's ~1e-11 relative-error estimate at
   each swept size, since this path is not bit-identical to stock (unlike
   OPP-000007's shipped `intersect_sorted`); decide if PyOverdrive's
   correctness policy accepts an approximate result.
4. Confirm the naive path stays default for object-dtype arrays and
   `mode='valid'` single-lag calls, per cournape's objections.
5. Track numpy/numpy#22255 and scipy/scipy#2651 as precedent for the "FFT
   as an opt-in parameter" API shape already proposed elsewhere.

## Does it reproduce (2026-08-23, fp 8f8198d9abab, numpy 2.4.5, contended box)

FFT full-mode convolution/correlation reproduces, and at scale beats the
171.4x claim floor outright: at n=20000 float64, `fft_rfft_irfft` hits
1518.3x on convolve and 1468.6x on correlate (both ~3.1-3.4s baseline down
to ~2.0-2.3ms). Int64 wins by far less at the same n, 62.4-67.9x, because
the naive int64 baseline is already slower per element and the FFT-int
variant pays a cast-to-complex tax. The win narrows sharply at small n but
never reverses: n=1000 float64 is the worst case tested, 2.33-2.96x, still
a real win, not a loss. All 12 cases (float64/int64 x correlate/convolve x
n in {1000, 5000, 20000}) came back correct=true; no candidate lost to the
naive baseline anywhere in this sweep. A transparent PyOverdrive fast path
looks worth shipping, gated on a length threshold well above n=1000 (where
the win is real but modest) so the crossover N* captures the regime where
the win is large, same-dtype non-object float/int 1-D arrays in
`mode='full'`/`'same'`, leaving `mode='valid'` and object dtype on naive
per cournape's objection.
