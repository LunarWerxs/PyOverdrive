# OPP-000003: ufunc.at (np.add.at) slow for grouped/indexed accumulation

## What is slow

`np.add.at(out, idx, vals)`, and `ufunc.at` in general, is the documented way to
accumulate values into an output array at possibly-repeated indices (the operation
`out[idx] += vals` cannot itself do this correctly when `idx` has duplicates,
because fancy-index assignment does not accumulate, it overwrites). The two source
issues report `ufunc.at` running 10-25x slower than hand-written or specialized
alternatives for this pattern, with one maintainer quick-test showing `np.bincount`
roughly 60x faster than `np.add.at` on a 100,000-element case, and a separate
reporter's pybind11 extension roughly 40x faster.

## Why, per the thread

`jaimefrio` traced the mechanism directly (comment on #5922, 2015-05-28): a normal
ufunc call fills a large contiguous buffer, casts/aligns it once, runs the inner
loop over the whole buffer, then copies out. `ufunc.at` cannot do that, because if
the same output index appears twice in one buffer, the two contributions would not
be accumulated correctly against each other. So it falls back to single-item
buffers via the generic `NpyIter` machinery, reset for every element, meaning every
single accumulation pays full casting and alignment overhead one at a time instead
of once per buffer. He found a ~6x speedup was reachable by adding an aligned,
non-byteswapped, no-cast fast path, but noted the general case (arbitrary dtypes,
multi-dimensional indices, arbitrary ufuncs) would still be far short of
`bincount`. `seberg` agreed the slow casting path was known and inefficient but
pushed back on the premise that `ufunc.at` should ever match `bincount`, which is
narrowly specialized (1D, addition only, `intp` indices, contiguous).

## Who reported it, and when

`d1manson` opened #5922 on 2015-05-27, motivated by building a Matlab-style
`accumarray` function and finding `ufunc.at` was the obvious tool for the job but
performed far worse than hand-vectorized alternatives for `sum`, `mean`, `std`,
`var`, `any`, `all`. `nschloe` opened #11156 independently on 2018-05-24 after
finding `numpy.add.at` dominating runtime in his own code and writing a C++
(pybind11) replacement roughly 40x faster; it was marked a duplicate of #5922.

## Maintainer objections

- Generality tradeoff: `bincount` only handles 1D addition over `intp` indices and
  `double` weights; `ufunc.at` supports multidimensional indices, arbitrary dtypes,
  and almost any ufunc, so a large part of the gap is the price of that generality
  (`jaimefrio`).
- Skepticism that parity with `bincount` was ever the right bar: "silly to expect
  it to be as fast as bincount... bincount is pretty specialized" (`seberg`).
- Resourcing, not disagreement: `seberg` (2017) said the fix was not "impossibly
  complicated" but needed "quite a bit of time and spare brain cycles" that
  maintainers were short on, which is largely why it sat open for eight years.
- Narrow semantics behind competing benchmarks: `mattip` pointed out the fastfunc
  40x number only holds for `int64` data with no overflow/divide-by-zero handling
  and no broadcasting, i.e. it is not a like-for-like replacement.

## What existing projects/PRs attempted

`numpy-groupies` (d1manson + ml31415, pip-installable) and `fastfunc` (nschloe,
pybind11) both exist specifically to route around slow `ufunc.at`. On the NumPy
side, `jaimefrio` published an experimental `ufunc_at_fast` branch (never merged),
followed by `mattip/numpy#72` and `numpy/numpy#22889` (fast paths for cases needing
no casting), and finally `numpy/numpy#23136`, "create and use indexed inner
loops", which merged and closed both #5922 and #11156 on 2023-02-08. A follow-up
enhancement, `numpy/numpy#22907`, added `initial`/`out` parameters to `bincount`
itself. Issue `numpy/numpy#23176`, "make ufunc.at faster for more cases", remains
open, implying #23136 did not close every gap (most likely multi-dimensional
indices or dtype-casting cases).

## What semantics differ

`bincount` is addition-only, 1D, `intp` indices, and effectively `float64`/`intp`
weights; it cannot express `min`, `max`, `multiply`, or any other ufunc, and it
cannot take multi-dimensional index arrays the way `ufunc.at` can. Fast
specialized alternatives (fastfunc, the `numpy-groupies` non-`ufunc.at` paths)
typically hardcode a handful of operations and assume matching dtypes with no
overflow/divide-by-zero handling and no broadcasting. Any PyOverdrive acceleration
of `ufunc.at` itself must preserve full generality (arbitrary ufunc, arbitrary
dtype pair with casting, multi-dimensional fancy indexing); accelerating only the
addition/1D/no-cast case would really be re-deriving `bincount`, not fixing
`ufunc.at`.

## Is it common enough to matter

Grouped or indexed accumulation (histogram-style aggregation, "groupby-sum" over
an index column, scatter-add in ML feature aggregation) is a common numerical
pattern, and the sustained interest across two issues spanning 2015-2023, plus two
independently maintained external packages built to avoid `ufunc.at`, is a
reasonable signal that real workloads hit this.

## What PyOverdrive should do next

The core finding for this project is that NumPy already merged a real fix
(`numpy/numpy#23136`) in the 2023 development cycle, and the installed benchmark
environment here runs NumPy 2.4.5, well past that merge. The post-fix benchmark
posted by `nschloe` in the issue thread shows `add.at` leveling off to roughly
match `bincount` at large n (both become memory-bound), with `seberg` noting some
residual overhead is still expected at smaller n. Before investing in any
acceleration, PyOverdrive should run the written reproducer
(`benchmarks/historical/opp_000003_ufunc_at.py`) across a range of `n` and group
count `k` to establish how much gap, if any, remains on current NumPy, paying
particular attention to small/medium n (where fixed per-call overhead would show
up most) and to the open case named by `numpy/numpy#23176`. If the measured gap is
now small, this record should likely close as `superseded` by the upstream fix
rather than proceed to prototyping.
