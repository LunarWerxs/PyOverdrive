# OPP-000004: cache-blocked plus threaded relayout of large 2-D arrays

Source: https://github.com/numpy/numpy/issues/21655 (numpy/numpy #21655, open,
opened 2022-06-03, retrieved 2026-08-23)

## What is slow

Converting a large 2-D array between C order and F order (equivalently,
materializing the contiguous copy of a transpose, e.g.
`np.ascontiguousarray(a.T)` or `result[:] = a[:]` into an array allocated with
the other order) is reported as needlessly slow for large matrices. The
reporter, orenbenkiki, says this is "a serious concern if the data is large"
and that the naive numpy path is "needlessly slow" once the matrix no longer
fits in cache.

## Why, per the thread

Relayout touches every element exactly once but with a stride pattern that
defeats spatial locality in one of the two directions: walking the source in
its natural order writes the destination with a large stride (or vice versa),
so most writes (or reads) miss the cache line entirely. Numpy's naive strided
copy does not tile the traversal to keep both access patterns within a cache
line's worth of reuse, so at large sizes it pays a cache-miss penalty on every
element. stevengj's follow-up spells out the mechanism: because out-of-place
transposition has no temporal locality (each element moves exactly once),
what matters is cache-line length (spatial locality), not cache capacity, so
a portable tiled implementation need not even sniff hardware cache sizes.

## Who reported it and when

orenbenkiki opened the issue on 2022-06-03 with a proposed new API,
`numpy.asorder(a, order, inplace=False)`, and a benchmark script comparing
numpy's naive relayout against a hand-written pure-Python cache-blocked
implementation (nested small/large block tiling, optionally parallelized 1-4
threads via `ThreadPoolExecutor`). Two comments followed: baumdan1 on
2022-06-05, agreeing and noting the potential for vectorization, and
stevengj (FFTW's author) on 2023-06-07, a year later, giving the
cache-oblivious-vs-cache-blocked tradeoff detail above.

## Maintainer objections

None on record. No numpy core maintainer has triaged, labeled, or commented
on this issue in the more than four years it has been open as of retrieval;
it carries no labels. The only pushback-adjacent comment is stevengj's steer
away from the reporter's hand-tuned block-size approach toward a recursive
cache-oblivious algorithm for portability, plus a warning that FFTW's own
tiled out-of-place transpose code is GPL-licensed and must not be lifted into
numpy verbatim. Treat this record as unreviewed, not maintainer-endorsed.

## Existing projects and PRs

No PR is linked to this issue and none exists in numpy implementing
`asorder` or a tiled relayout kernel. stevengj cites two external precedents
instead: Julia's out-of-place transpose, using a recursive cache-oblivious
algorithm (JuliaLang/julia#6690), and FFTW's `cpy2d.c`, which uses a fixed
8 KiB tiling buffer for out-of-place and square in-place cases plus a more
complex poly-algorithm (`vrank3-transpose.c`) for the non-square in-place
case. FFTW's code is GPL and flagged as unsuitable to copy into numpy.

## Semantics

A relayout is a pure data-movement operation: same values, same shape (or its
transpose), different strides. There is no rounding or reordering ambiguity
to introduce, so correctness reduces to an exact equality check between
candidate and baseline output, not a tolerance comparison. The one open
semantic question raised in the thread (`a.reshape(a.shape, order='F')`
returning C-order output) is a separate, unconfirmed report and out of scope
here.

## Is it common enough to matter

Relayout is a common preparatory step before row-wise or column-wise
reductions, BLAS calls that require a specific order, or interop with
column-major libraries, and the reporter frames it as a real cost at the
~1 GB+ scale genomics/large-matrix workloads hit. That said, the only
evidence in the issue is one reporter's own microbenchmark; no other numpy
user has chimed in beyond the two comments, so community pull is thin
compared to well-trafficked issues.

## What PyOverdrive should do next

Treat this as a native-kernel candidate, not a drop-in numpy patch: the
issue's own "fast" path is Python-level threading over numpy slices, not a
released-GIL C kernel, so it cannot show numpy's true ceiling. Establish a
fingerprinted baseline for `np.ascontiguousarray(a.T)`-style relayout across
size and dtype (this record's reproducer) before attempting a tiled kernel,
and read the Julia and FFTW precedents for tiling strategy rather than
re-deriving one. Because there is no maintainer signal either way, budget
this as "reproduce the cost, do not assume numpy would accept it" until an
upstream conversation is independently pursued.

## Does it reproduce (2026-08-23, fp 8f8198d9abab)

Partially with the issue's own per-call-executor candidate: 2.1x float32 and
1.5x float64 at 4096x4096, 1.1-1.4x from 1024 up, a loss at 512
(`benchmarks/results/OPP-000004/`). Fully once the tiling runs on a
persistent pool: see below.

## Shipped: `relayout_blocked`

Status: performance_validated. `np.ascontiguousarray(x)` for a plain 2-D
F-contiguous, non-C-contiguous float64 / float32 / int64 array at or above
512x512 (int64: 1024x1024) is rerouted to a tile-256 blocked copy spread
over the PyRallel pool (8 threads, 16 from 2048x2048), each block being a
stock slice assignment, so the result is a bit-identical fresh C copy. The
189-variant `RELAYOUT-CAL` battery (tile 64/128/256 x 4/8/16 threads x 3
dtypes x 7 shapes, at 83-99% foreign load) measured float64 2.0x at 512x512
to 3.8x at 2048-4096 square; float32 4.4x at 1024x1024, 5.6x at 4096x4096
and 6.6x at 8192x1024, which is the issue's claimed ceiling; int64 2.0-3.4x
from 1024x1024. 256x256 loses at every setting and is below the floor;
int64 512x512 (1.0-1.3x) is excluded. Already-C-contiguous input, any
keyword, other ndims and dtypes stay on stock. Reach: only the explicit
`np.ascontiguousarray` name; `x.copy(order="C")`, `np.array(x)` and
`np.asarray(x, order="C")` are not patched.
