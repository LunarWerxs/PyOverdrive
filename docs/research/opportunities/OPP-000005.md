# OPP-000005: CPython call-site specialization for NumPy dispatch overhead

## What is slow

Not a single operation but a systemic cost: every NumPy ufunc call redoes its
"work planning" from scratch, casting rules, broadcasting shape resolution,
`__array_ufunc__` override checks, dtype resolution, on every invocation, even
when a given call site sees the same types and shapes on every pass through a
hot loop. For small to medium arrays this per-call fixed overhead dominates
the actual arithmetic, since the arithmetic itself is cheap at small n.

## Why, per the thread

CPython 3.11 introduced bytecode "quickening": a generic instruction observed
running with consistent types at a given bytecode offset gets replaced with a
type-specialized instruction that skips the generic dispatch path. A 2024
ECOOP paper (linked by mdboom, the issue author and a CPython Faster-CPython
team member) proposes extending that same call-site caching idea to
extension types, so a NumPy ufunc call site could cache its casting and
broadcasting decisions and skip that planning on repeat calls. The paper
reports gains "on the order of more than 2x" for small-to-medium arrays using
prototype patches against both CPython and NumPy.

## Who reported it and when

mdboom (Michael Droettboom, Faster CPython team) opened the issue 2024-09-23
as an ENH discussion, seeking NumPy maintainer interest before committing to
build the CPython side. Active discussion ran through 2024-10-03 among
mhvk, seberg, eendebakpt, rgommers, and the paper's author fberlakovich. The
issue remains open with no forward motion recorded after that date (as of
retrieval 2026-08-23, nearly two years later).

## Maintainer objections

- **rgommers**: the paper never defines "small to medium sized," and without
  a size-vs-speedup curve the benefit is unquantified; also states this
  needs a full NEP, covering SIMD interaction, third-party dtype/Cython/
  Numba interaction, C API stability, and binary size/build time costs.
- **seberg**: suspects much of the measured gain is actually an unrelated
  result-object cache, not the specialization itself, and worries an
  unbounded cache leaks memory; ufunc-internal optimizations might
  independently shrink the benefit over time anyway.
- **mdboom** (proposer, but stating a real constraint): the real payoff needs
  BOTH CPython and NumPy participating, so CPython 3.14 at the earliest;
  bytecode is an unstable implementation detail with no deprecation cycle,
  making a stable "replace this bytecode" API hard to design without being
  brittle to whatever the interpreter does next.

## Existing projects/PRs

None inside numpy/numpy. The only code is two external forks used for the
paper's prototype: `fberlakovich/cmq-numpy-ae` (NumPy side, one squashed
commit using ad hoc mako templates instead of NumPy's existing code
generator) and `fberlakovich/cmq-ae` (CPython side). Related prior art:
`faster-cpython/ideas#696` (earlier discussion), and mhvk's own
`mhvk/chain_ufunc` experiment, a different angle on the same "avoid
redundant per-call overhead" problem via fusing ufunc calls instead of
caching one call's dispatch decisions.

## What semantics differ

None proposed to change user-visible semantics; this is an internal
dispatch-caching mechanism. The risk is architectural: new, non-limited C
API surface (opt-in at NumPy build time per mdboom), and a correctness
hazard if a cached "usual case" plan is reused when a call site's types
silently drift (e.g. usually `int + int`, occasionally `float`), needing a
guard/invalidation path the discussion never specified.

## Is it common enough to matter

Plausibly, since small-array ufunc calls in hot Python loops are common
(scalar-like per-element ops, small data pipelines), but the thread never
establishes a concrete size threshold or workload profile, the open
question rgommers raised and nobody answered. Without that curve, "common
enough" cannot be assessed from the issue alone.

## What PyOverdrive should do next

PyOverdrive cannot replicate the CPython-side quickening (that requires a
non-standard interpreter build), but it can attack the same overhead
NumPy-side: eliminating redundant work-planning per call via its own
call-site memoization, without waiting on CPython 3.14 adoption. The baseline
reproducer here (`opp_000005_call_overhead.py`) measures how much of the
per-call floor is pure dispatch and allocation overhead (comparing
`np.add(a, b)`, the `+` operator, and a preallocated `out=` call across
sizes) so a future prototype has the size-resolved overhead curve rgommers
asked for and never got. Status stays `unverified`/exploratory until that
curve exists; this is a multi-year-stalled discussion, not an
implementation ready to adopt.

## Does it reproduce (2026-08-23, fp 8f8198d9abab)

Not reproduced. The CPython-side quickening mechanism cannot be tested in
stock NumPy, so the baseline_only reproducer measured the overhead ceiling
it would need to attack: `np.add(a, b)` vs `a + b` vs a preallocated
`out=` call, across n in {4, 64, 1024, 65536} on numpy 2.4.5. The best
result anywhere in the sweep is `preallocated_out` at n=1024 (742.6ns ->
582.0ns, 1.28x); the operator form tops out at 1.18x (n=4, 449.6ns ->
379.4ns). Every case falls well short of the claimed >2x. Stock NumPy does
carry real per-call dispatch/allocation overhead, but the addressable
ceiling on this machine is roughly 1.05x-1.28x, not 2x. Full data:
`benchmarks/results/OPP-000005/8f8198d9abab.json`.
