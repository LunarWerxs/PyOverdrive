# OPP-000014: np.unique(arr, axis=0) slow for trivial single-column 2-D arrays

Source: numpy/numpy#15713, "np.unique(arr, axis) slow for axis=0", opened by
mganahl on 2020-03-05. State at ingestion: open, no timeline events beyond
comments, labels `component: numpy.lib` and `33 - Question`. This is a
question-labeled issue with maintainer replies, not a settled or rejected
proposal, and not a PR.

## What is slow

`np.unique(arr, axis=0)` is markedly slower than `np.unique(arr)` even when
the 2-D array is a trivial expansion of the same 1-D data: `mat =
np.expand_dims(arr, 1)`, i.e. shape `(N, 1)`, where the memory order of the
elements is identical to the 1-D case. The reporter's repro times both calls
over a 100-iteration loop and reports the axis=0 call as "~10 times slower."

## Why (per the thread)

seberg explains the mechanism: the axis=0 implementation has to "ensure that
the "elements" being compared are contiguous in memory," which means turning
each row into an "element" via a structured dtype view, and comparing/sorting
with structured-dtype machinery. For a single-column array this buys nothing,
since there is nothing to make contiguous that is not contiguous already, but
the implementation does not special-case it: "it mainly adds a large chunk of
overhead due to using structured dtype defined comparison/sorting, which does
not optimize for the trivial case you got here."

## What semantics differ

None, for the narrow single-column case: ravelling a `(N, 1)` array to 1-D
and back is a lossless, order-preserving reshape, so a fast path restricted
to `arr.shape[1] == 1` returns bit-identical results to the general axis=0
path. Semantics only become a live question for the broader ask eric-wieser
raises (reintroducing the general multi-column optimization): seberg flags
that the removed approach made sorting order depend on byte-order, and
separately warns that this class of trick is "dangerous in general" - a real
correctness caveat, not resolved in this thread.

## Is it common enough to matter

Narrowly, yes, for the exact trivial-expansion shape in the repro (a caller
who reshapes a 1-D array to `(N, 1)` and then calls `unique(..., axis=0)`
instead of just calling `unique` on the 1-D array) - but that shape is also
somewhat of a self-inflicted case; a caller who already knows the array is
effectively 1-D could just call `np.unique(arr)` directly. The more general
multi-column axis=0 case (real row-uniqueness on genuine 2-D data, e.g.
DominicAntonacci's "unique 2D points" use case) is plausibly common in
data-processing code, but the thread supplies no benchmark numbers for that
general case, only the trivial one.

## What PyOverdrive should do next

1. Write a Dyno reproducer comparing `np.unique(arr, axis=0)` against
   `np.unique(mat, axis=0)` where `mat = np.expand_dims(arr, 1)`, against a
   ravel-and-reshape fast path (`np.unique(arr).reshape(-1, 1)`), sweeping
   sizes `[1000, 10000, 100000, 1000000]` and dtypes `[int32, int64, uint32,
   uint64, float32, float64]`, to establish whether the reported ~10x holds
   at scale and across dtypes, not just at the reporter's N=1000 int sample.
2. In the same reproducer, add a genuine multi-column case (e.g. random
   `(N, 3)` and `(N, 8)` integer arrays with duplicate rows) against
   DominicAntonacci's lexsort-based `unique_axis0` and against stock
   `np.unique(..., axis=0)`, since the thread gives no quantitative evidence
   for the general case and it is the more common real-world shape.
3. If the single-column ravel fast path reproduces a real, bit-identical
   win, that is the shape PyOverdrive's dispatch is built for: detect
   `arr.ndim == 2 and arr.shape[1] == 1` (or the axis=0 argument reducing to
   a single-column view) cheaply and route to the 1-D `unique1d` path with
   no new keyword and no semantic change.
4. Treat the general multi-column optimization as a separate, higher-risk
   follow-up gated on resolving seberg's byte-order-sorting objection and
   eric-wieser's "stricter whitelist of types," not bundled into the
   single-column fast path.
5. Check PR numpy/numpy#10588 directly (not just the thread's description of
   it) to confirm what the original optimization covered and why it was
   removed, before deciding how much of it PyOverdrive should reintroduce
   independently of upstream.

## Does it reproduce (2026-08-23, fp 8f8198d9abab, numpy 2.4.5, contended box)

Reproduces. The claim's own regime (N=1000, single-column, int64) measured
10.2x (375369 ns -> 36808 ns), an almost exact match to the reported ~10x.
Across the single-column sweep (int32/int64/uint32/uint64/float32/float64,
N in [1000, 10000, 100000, 400000]) the ravel_reshape fast path won every
case, 2.2x-66.2x, with the best case float32 N=100000 at 66.2x (55678300 ns
-> 840471 ns). It loses ground at large N: N=400000 ranges only 2.2x
(uint64) to 6.0x (uint32). A separate lexsort candidate for the broader
multi-column axis=0 case also won everywhere but far more modestly,
1.10x-4.37x, with 8-column N=100000 barely above parity. All 30 cases were
bit-correct on both candidates. Box was contended during the run
(conditions.contended=true), so absolute times carry noise, but the
near-exact match to the claim at N=1000 and the size of the wins elsewhere
survive that. A transparent PyOverdrive fast path looks worth shipping for
the single-column case specifically, gated on the cheap `arr.ndim == 2 and
arr.shape[1] == 1` predicate noted above; the multi-column path is a
separate, smaller, higher-risk win not worth bundling in yet.
