# OPP-000024: Integer-view fast path for np.unique on single-character U1/S1 arrays

Source: numpy/numpy#24821, "ENH: Sorting single-character arrays (S1 / U1)
using integer sorting", opened 2023-09-27 by smsaladi. State at ingestion:
open. Label: `01 - Enhancement` (added by melissawm, 2023-10-06). Zero
comments; everything below comes from the issue body, which itself quotes
an ngoldbaum reply from the numpy-discussion mailing list
(https://mail.python.org/archives/list/numpy-discussion@python.org/thread/VF43XVYRFWVUVCMOFPEEI73EVUJ6MRVI/).

## What is slow

`np.unique` on a single-character string array (dtype `U1` or `S1`) is
substantially slower than the same call routed through an integer
reinterpretation of the same buffer. The reporter's own benchmark, in the
issue body:

```python
charlist_10k = np.array(list('ASDFGHJKLZ' * 1000), dtype='U1')

def unique_basic(x):
    return np.unique(x)

def unique_view(x):
    return np.unique(x.view(np.int32)).view(x.dtype)
```

At 10,000 elements: `unique_basic` 204 us +/- 4.61 us vs `unique_view`
66.7 us +/- 2.91 us, a derived 3.06x (204 / 66.7; the thread never states
the ratio itself). At 10 elements the view path loses: 2.17 us vs 2.53 us,
a derived 0.86x, so there is a crossover somewhere between 10 and 10,000
elements that the thread does not locate. The reporter says the pattern
held across variations they tried ("S1 vs U1; int32 vs int64;
return_counts = True vs False; 100, 1000, or 10k elements") but posts
numbers only for the U1/int32 pairs above. Hardware and numpy version are
never stated.

## Why (per the thread)

The quoted ngoldbaum mailing-list excerpt gives the mechanism from a
py-spy profile: "the difference comes down to NumPy's sorting
implementation simply being faster for ints than unicode strings. In
particular, it looks like string_quicksort_<npy::unicode_tag, char> is two
or three times slower than quicksort_<npy::int_tag, int> when passed the
same data." `np.unique` sorts internally, so the string-vs-int sort-kernel
gap dominates once the array is big enough to amortize the two extra view
calls. The reporter's surprise is that `np.unique` "knows" the input is
U1/S1 "and could handle the view-stuff internally" - which is exactly the
transparent fast path shape.

excerpt quoted in the body (so dated here 2023-09-27, the body's post

special case in the sorting code to improve performance for sorting
single-character arrays. I have no idea if that would be complicated or
would make the code difficult to deal with. I'll also note that string
sorting is a more general problem than integer sorting, since a generic
string sort can't assume that it is handed single-character strings."

The caveat cuts in PyOverdrive's favor: upstream would have to thread a
special case through the generic string-sort machinery, while an external
fast path only has to recognize the single-character case at the
`np.unique` call boundary and never touches the general sorter.

## What a transparent fast path would look like

Predicate sketch (all must hold):

1. Call is `np.unique(a, ...)` with no `axis` argument.
2. `a.dtype.kind` is `'U'` with `itemsize == 4` (U1), or `'S'` with
   `itemsize == 1` (S1).
3. Dtype byte order is native (byte-swapped arrays excluded, or
   byteswapped to native first and the cost counted).
4. `a.size >= N*`, a calibrated threshold; the thread brackets the
   crossover only between 10 and 10,000 elements.

Route: view U1 as `int32`, S1 as `uint8`; call stock `np.unique` on the
integer view, passing `return_index` / `return_inverse` / `return_counts`
through untouched; view the values array back to the original dtype.

Why the result is bit-identical, and the two hazards that make it so only
if the view targets are chosen correctly:

- U1 -> int32: numpy orders U1 by its single UCS4 code unit, and every
  valid codepoint (<= 0x10FFFF) is non-negative in int32, so the view is
  a strictly monotone bijection: same sort order, same equality classes,
  therefore identical values, indices, inverse, and counts.
- S1 -> uint8, never int8: S1 compares as unsigned bytes. A signed int8
  view would order bytes >= 0x80 before 0x00 and silently corrupt both
  the order and (for return_index) which duplicate is reported. This is
  the one real correctness trap in the whole opportunity.
- The empty string ('' in U1, b'' in S1) is stored as code unit / byte 0
  and sorts first under both representations; no special case needed.
- Byte-swapped dtypes break the codepoint-equals-integer identity and
  must stay on the stock path (predicate 3).

Semantics beyond ordering are untouched: no tolerance, no approximation,
no dtype change visible to the caller. This is the best kind of corpus
entry - the candidate is exact by construction - and the risk fields in
the YAML are `low`/`low` accordingly.

## Is it common enough to matter

Unproven. Single-character arrays are a real pattern (sequence data - the
reporter's handle suggests bioinformatics - categorical codes, genotype
matrices), but the issue drew zero comments and no reactions in over two
years, and the workaround is trivial for anyone who finds it. The counter:
that is precisely the profile of a fix nobody upstream will prioritize
(ngoldbaum flags the general-sorter complication) while a call-boundary
fast path gets it for free. Demand evidence should be treated as weak
until Dyno numbers say the win is large.

## What the Dyno reproducer must measure

1. Baseline `np.unique(x)` vs candidate `np.unique(x.view(np.int32)).view(x.dtype)`
   for U1, and the `uint8` equivalent for S1, on current numpy - the
   thread's numbers are from an unstated version filed 2023-09-27, and the
   string sort may have changed since.
2. Size sweep 10, 100, 1_000, 10_000, 100_000, 1_000_000 to locate the
   crossover N* the thread leaves between 10 and 10k, and to see whether
   the 3.06x grows or shrinks at sizes the reporter never ran.
3. `return_counts` False and True (reporter claims the pattern holds for
   both; only False is evidenced), plus one `return_index`/`return_inverse`
   case to prove passthrough correctness.
4. Alphabet-size axis: the repro uses 10 distinct characters; run at least
   one large-alphabet case (e.g. full ASCII, and a non-Latin codepoint set
   for U1 to exercise values above 0x7F, which is also the int8-vs-uint8
   trap detector for S1).
5. Correctness gate: exact array equality on every returned array
   (values, index, inverse, counts) against stock output; nothing weaker.
6. A separate `np.sort`-only pair (U1 vs int32 view) to isolate
   ngoldbaum's "two or three times slower" sort-kernel figure from the
   unique-level end-to-end ratio, since a shipped fast path could
   plausibly cover `np.sort`/`np.argsort` on U1/S1 too even though the
   thread only measures `np.unique`.
