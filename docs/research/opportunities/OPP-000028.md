# OPP-000028: Sorted-input fast path for np.argsort (numpy 2.x AVX2 regression)

Source: numpy/numpy#28714, "BUG: Performance regression in argsort on sorted
data", opened 2025-04-15 by rhshadrach. State at ingestion: open. Label:
`00 - Bug`. Four comments, all on 2025-04-15; retrieved 2026-08-24.

## What the issue claims

From numpy 1.26.4 to 2.0.0, `argsort` on already-sorted data got much
slower, while non-sorted data got faster ("On non-sorted data, I am seeing
a performance enhancement when upgrading to 2.0"). The reporter's repro:

```python
N = 10**5
arr = np.arange(N)
%timeit arr.argsort()
# 1.59 ms  <-- 2.0
# 1.6 ms   <-- 2.2.4
# 444 us   <-- 1.26.4
```

Derived from those numbers, the regression is 1590/444 = 3.58x on numpy 2.0
and 1600/444 = 3.60x on 2.2.4, so it persisted at least through 2.2.4. The
context is pandas moving its dev pin to numpy 2.0+ and "working through the
identified performance regressions" (pandas-dev/asv-runner#50). Environment:
Linux x86_64 (Ubuntu), Haswell-class CPU with AVX2 but no AVX512, Python
3.12.3.

## Why (per the thread)

charris triaged same-day ("Possibly related, #23707, #25610.") and pinged
r-devulap, who confirmed the cause: "this is because of the AVX2 argsort
introduced in https://github.com/numpy/numpy/pull/25610 which unfortunately
has regressions for ordered arrays specially on 64-bit dtypes." His ASV
table quantifies it verbatim: `time_argsort('quick', 'int64', ('ordered',))`
went from 63.8us before the AVX2 branch to 260us after, ratio 4.07.

The thread does not spell out the micro-mechanism beyond attributing it to
the AVX2 kernel. The standard reading (interpretation, not from the dump):
a vectorized quicksort/partition network does its full partitioning work
regardless of pre-existing order, where the previous path was cheap on
ordered input; branchless SIMD code gives up exactly the adaptivity that
made sorted input a best case.

## Upstream fix status - why this record is unverified

This is the load-bearing fact: **the fix probably already shipped.**
r-devulap was "working on a fix for this in
https://github.com/intel/x86-simd-sort/pull/197" and hours later posted
"Fix for this is now part of: https://github.com/numpy/numpy/pull/28619".
The cross-referenced PR object in the dump shows PR 28619 ("ENH: Use openmp
on x86-simd-sort to speed up np.sort and np.argsort") **merged
2025-05-14T21:46:38Z** into the "2.3.0 release" milestone, and its body
explicitly lists "Fixes `np.argsort` perf regressions on sorted data (as
reported in: https://github.com/numpy/numpy/issues/28714)". Its own ASV
table (TGL, 500,000 elements) shows argsort int64 ordered going 9.50ms to
3.08ms (ratio 0.32) - though the same table introduces new '+' rows for
32-bit 'uniform' patterns (ratios 1.29-1.49), so the openmp rework has its
own tradeoff surface. The issue was never closed.

So the claim window is numpy 2.0 through at least 2.2.4. Anything we say
about current numpy is a guess until the Dyno runs.

## What a transparent fast path would look like

Even a complete upstream fix leaves a residual opportunity: detecting
sortedness and skipping the sort entirely is O(n) versus O(n log n), and
even never-regressed 1.26.4 spent 444us argsorting the reporter's sorted
100k array. Whether that residual clears the ship bar is a measurement
question, not a thread question.

**Predicate sketch.** Intercept `np.argsort` / `ndarray.argsort` when all
of: input is 1-D, C-contiguous, native integer dtype (int64 first, the
measured regime); `axis` is default; `order is None`; `kind` is default or
'stable'; and an early-exit scan finds `a[i] < a[i+1]` for all i (strictly
increasing). On predicate pass, return `np.arange(n, dtype=np.intp)`.

**Route.** Strictly-increasing input makes the argsort permutation unique,
so `arange` is bit-identical to stock for every sort kind - no numerical
tolerance argument needed, same class of exactness as a semantics-preserving
dispatch.

**Semantics hazards.**

- *Ties.* For merely non-decreasing input, stock quicksort's tie order is
  unspecified-but-concrete; `arange` is a valid answer but may differ
  bitwise from stock. `arange` IS exactly stock for `kind='stable'` (stable
  sort preserves original order of equal keys). Ship strict-increase-only
  first; optionally extend to non-decreasing under `kind='stable'`.
- *Floats.* A naive comparison scan mishandles NaN, whose sort position
  numpy defines (NaNs sort to the end). Integer dtypes sidestep this
  entirely; a float extension needs a NaN-aware scan.
- *Guard cost on non-sorted input.* The reporter says random input got
  FASTER in 2.0; the fast path must not give that back. Early exit on the
  first inversion makes the expected guard cost on random data trivial
  (a few comparisons); the adversarial case is a long sorted prefix with a
  late inversion - full O(n) scan paid, then the full sort anyway. The
  Dyno must price this.
- *Descending input.* Reversed data is not covered (a reversed `arange` is
  wrong under ties for stable sort, and the win is unmeasured). Out of
  scope for the first cut.

## What the Dyno reproducer must measure

1. **Does the regression still exist?** Stock `arr.argsort()` on ordered
   vs random int64 at N in {1e4, 1e5, 1e6} on current numpy. Ordered
   materially slower than random on the same size is the smoking gun; if
   ordered is now at or below random, PR 28619 did its job and the claim
   is historical.
2. **The fast-path headline.** sorted-scan + arange candidate vs stock on
   strictly-increasing input, same sweep. This replaces the 4.07x claim
   number with a real current-numpy figure.
3. **Guard-cost floor.** Candidate vs stock on random input (early exit)
   and on the adversarial almost-sorted input (inversion at index n-2):
   the loss there must be within noise or bounded to a few percent.
4. **Sweep dtypes and kinds.** int64 and int32; kind 'quick' (r-devulap:
   regressions hit "specially on 64-bit dtypes") and 'stable'; optionally
   float64 all-finite to size a future float extension.
5. **Correctness probes.** Bit-identical output vs stock on every strictly
   increasing case; a separate tie probe (non-decreasing input) recording
   where stock quicksort's permutation diverges from arange, to document
   why ties stay out of the predicate.

## Is it common enough to matter

Argsorting already-sorted data sounds degenerate but is exactly what hit
pandas' benchmark suite during its numpy 2.0 pin upgrade - the issue exists
because a major downstream felt it in CI, not from a synthetic microbench.
Beyond that single (well-placed) data point the thread is thin: 4 comments
in one day, zero reactions, and a maintainer fix in flight within 8 hours.
Demand evidence is real but narrow; the fix-already-merged risk is the
dominant reason this is unverified rather than queued for implementation.

## Maintainer objections

None against fixing; the risk to PyOverdrive is the opposite - it may
already be fixed. On record from r-devulap (MEMBER, both 2025-04-15): the
diagnosis quote and "Fix for this is now part of:
https://github.com/numpy/numpy/pull/28619". A PyOverdrive fast path scoped
to provably-sorted input is complementary rather than competing: it wins by
skipping the sort, not by re-tuning the kernel, and has no uniform-pattern
tradeoff surface like the openmp rework's '+' rows.
