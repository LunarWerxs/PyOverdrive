# OPP-000020: contiguous-copy fast path for np.dot / np.matmul on non-contiguous arrays

Source: numpy/numpy#19650, "Improve dot performance on data that isn't
contiguous", opened by akhmerov on 2021-08-11. State at ingestion: open,
labels `01 - Enhancement` and `component: numpy.ufunc`. Last recorded
activity in the fetched thread is 2021-10-19; no comments after that date
are present in the retrieved data.

## What is slow

`np.dot` and the equivalent `@` / `np.matmul` call on non-contiguous array
views can be dramatically slower than the same product computed after an
explicit copy to a contiguous layout. The reporter's own microbenchmark, on
numpy 1.21.1:

```python
a = np.random.randn(1000, 100, 1000)
%timeit a[:, 0, :] @ a[:, :, 20]
# 1.59 s +/- 184 ms per loop (mean +/- std. dev. of 7 runs, 1 loop each)
%timeit np.ascontiguousarray(a[:, 0, :]) @ np.ascontiguousarray(a[:, :, 20])
# 8.06 ms +/- 410 us per loop (mean +/- std. dev. of 7 runs, 100 loops each)
```

That is 1.59 s versus 8.06 ms for the same matrix product, a computed ratio
of 197.27x, and the second timing already includes the cost of the two
`ascontiguousarray` copies -- it is not a number that hides the copy.

## Why (per the thread)

akhmerov's diagnosis: `a[:, 0, :]` and `a[:, :, 20]` are both non-contiguous
views produced by indexing a middle or last axis of a 3-D array, so the
general dot-product code path walks memory with a generic strided-access
pattern instead of handing a BLAS routine a clean contiguous buffer. Because
the workaround (copy first, then multiply) is easy to write but easy to
miss, the reporter argues the regression is "hard to detect, and many users
won't even be aware about it," and proposes NumPy itself "identify when data
is highly discontinuous and copy it before performing the multiplication."

## What semantics differ

None. `np.ascontiguousarray` reproduces the same values in a new,
contiguous buffer before the same multiply runs; this is a relayout, not a
different algorithm, so the result is bit-identical to the non-contiguous
path. The question the thread never settled is purely a performance
heuristic: when the copy is worth its own cost, since copying a small or
already-cheap array can make the "fast path" slower than doing nothing.

## Is it common enough to matter

Plausibly, for a specific access pattern rather than for arrays in general:
fixing one index while varying another on a multi-dimensional array (the
reporter's `a[:, 0, :]` / `a[:, :, 20]` shape) is a routine way to pull 2-D
slices out of a 3-D stack for repeated matrix products. But unlike
OPP-000007, no downstream library or use case is named anywhere in the
thread, the issue drew only two other participants over more than two
years, and no maintainer confirmed how often the regression bites in
practice -- so the addressable regime here is a plausible guess from one
reporter's single benchmark, not a corroborated claim.

## What PyOverdrive should do next

1. Write the Dyno reproducer: baseline `a[:, 0, :] @ a[:, :, 20]` against
   candidate `np.ascontiguousarray(a[:, 0, :]) @ np.ascontiguousarray(a[:, :, 20])`,
   starting from the reporter's exact array `a = np.random.randn(1000, 100, 1000)`
   (float64), then sweep the leading/trailing dimensions (e.g. 100, 500,
   1000, 2000 in place of 1000 and 100) and dtypes float32 and float64 (the
   BLAS-backed path this fast path would route to only applies to
   float32/float64/complex64/complex128) to find where the crossover
   between "copy pays for itself" and "copy is pure overhead" actually sits.
2. If the speedup reproduces on current NumPy across a meaningful size
   range, that crossover point is the predicate PyOverdrive's adaptive
   dispatch needs: detect non-contiguous 2-D+ float operands above a size
   threshold and route to an ascontiguousarray copy before the existing
   dot/matmul call, exactly automating the reporter's manual workaround.
3. Because the result is bit-identical (a relayout, not a new algorithm),
   correctness validation should be cheap relative to OPP-000007's; spend
   the validation effort on the heuristic threshold instead, since that is
   the part both akhmerov and seberg flagged as unresolved.
4. Cross-check against OPP-000004 (blocked transpose copy) and OPP-000002
   (np.inner ndim>2 via tensordot) before shipping, since all three touch
   the same underlying question of when NumPy should pay a copy cost to
   reach a BLAS-friendly layout -- a shared heuristic or shared copy-cost
   model may be more valuable than three separate ad hoc thresholds.

## Does it reproduce (2026-08-23, fp 8f8198d9abab, numpy 2.4.5, contended box)

No. Across all 10 tested cases (float32/float64, n in {100, 300, 1000},
m in {100, 500, 1000}) the ascontiguousarray-copy candidate never beats
plain `a[:,0,:] @ a[:,:,last]` -- every speedup is below 1.0x, correct=True
throughout, so this is a clean performance loss, not a correctness bug.
Worst: n1000_m100_float32 at 0.35x (717929 ns baseline vs 2058533 ns
candidate, ~2.9x slower) and n1000_m100_float64 at 0.39x (1425767 ns vs
3687650 ns). Least bad: n100_m1000_float32 at 0.93x (406643 ns vs
435100 ns) and n100_m100_float64 at 0.93x (32679 ns vs 35115 ns). Loss
gets worse as the copied operand's row count (n) grows relative to m --
the copy overhead scales with the larger view faster than the matmul it
is meant to speed up. The reporter's 197.27x is from numpy 1.21.1 on one
size point; on numpy 2.4.5's current BLAS dispatch the strided path is
evidently already fast enough that the explicit copy is pure overhead in
every regime swept here. A transparent PyOverdrive fast path here is not
worth shipping on this evidence: with zero winning cases out of 10, there
is no predicate to route on, and shipping it as-is would regress every
tested shape. Box was contended during the run, but a consistent sub-1x
result across 10 cases is not explained by noise.
