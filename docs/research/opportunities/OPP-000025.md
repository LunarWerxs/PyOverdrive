# OPP-000025: np.zeros_like ~53x slower than np.zeros(shape, dtype)

Source: numpy/numpy#9909, "np.zeros_like(a) is slower than
np.zeros(shape=a.shape)", opened 2017-10-23 by tarcisiofischer. State at
ingestion: open. No labels, no milestone, 4 thumbs-up reactions, last
comment 2018-10-15.

## What is slow

`np.zeros_like(a)` on a `(1000, 1000)` float64 array. The reporter timed
both legs in a Jupyter notebook with `%timeit -n100`:

- `np.zeros(shape=a.shape)`: 40.7 us +/- 5.72 us per loop (mean +/- std.
  dev. of 7 runs, 100 loops each)
- `np.zeros_like(a)`: 2.18 ms +/- 47.1 us per loop (mean +/- std. dev. of
  7 runs, 100 loops each)

The thread never states a ratio; 2180 / 40.7 = 53.56x is derived from the
reporter's own two numbers. Hardware, OS, and numpy/Python versions are not
given anywhere in the thread (2017 vintage, so pre-1.14 numpy).

## Why (mechanism)

The issue body links the then-current implementation
(`numpy/core/numeric.py` L138): `zeros_like` is `empty_like(a)` followed by
`multiarray.copyto(res, zeros(1, dtype=res.dtype), casting='unsafe')` -
allocate uninitialized memory, then physically write a zero into every
element. `np.zeros` instead gets its buffer via a calloc-style allocation:
for a large request (8 MB here) the OS hands back pages that are already
zero and are not faulted in until first touch, so "allocate 8 MB of zeros"
costs near-nothing at allocation time. The `copyto` path touches all 8 MB
immediately. The reporter's first comment links the StackOverflow
discussion of exactly this difference ("Why the performance difference
between numpy.zeros and numpy.zeros_like").

Corollary that matters for measurement: the 53x gap is an allocation-only
number. A consumer that writes the whole array afterwards pays the page
faults `np.zeros` deferred, so the end-to-end gap in real programs is
smaller than 53x; how much smaller is precisely what the Dyno run must
establish.

## Who reported and when

tarcisiofischer opened the issue 2017-10-23 with the benchmark and a
proposed reimplementation (dispatch to `np.zeros` when `subok` is false).
He offered to send a PR the same day but waited for "any more experienced
numpy dev" to react. tadeu added two correctness caveats on 2017-10-24.
hmaarrfk (CONTRIBUTOR) pushed back on the proposal's shape on 2018-10-15.
No comments since; no numpy maintainer ever weighed in; no PR is linked in
the dump's timeline.

## Objections raised in-thread

Nobody disputes the measured gap. All pushback targets the reporter's
proposed fix:

- tadeu (2017-10-24): it "should also work with 'array-like' objects, like
  lists of lists", fixable "using `np.shape(a)` instead of `a.shape`".
- tadeu (2017-10-24): "`dtype` and `order` should also be taken from `a`
  (unless passed explicitly, in this case they would be overridden)" -
  including string dtypes, where `zeros_like` of a `dtype=str` array fills
  with `''` (dtype `<U1`), not integer 0.
- hmaarrfk (2018-10-15): "I don't think your fix will address the majority
  of the use cases", namely `b = np.zeros_like(a)` "where the subok
  parameter is never specified, but `a` ... **is** a numpy array" - i.e. a
  gate on `not subok` never fires for the dominant calling pattern, which
  uses the `subok=True` default on a plain ndarray.

## What a transparent fast path would look like

Predicate sketch - intercept `np.zeros_like(a, dtype=None, order='K',
subok=True, shape=None)` and route to `np.zeros` only when ALL hold:

1. `type(a) is np.ndarray` exactly - not a subclass. This is hmaarrfk's
   objection turned into the gate: for a base ndarray, `subok` True or
   False yields the same base-class result, so the routing is valid for
   either flag value and fires on the majority pattern the reporter's own
   `not subok` gate missed. Subclasses (matrix, masked, units) stay on
   stock so subclass preservation semantics are untouched.
2. `shape` is None (no reshape requested) and `dtype` is None or a concrete
   numeric dtype. Non-ndarray array-likes (tadeu's lists-of-lists case) and
   exotic dtypes (object, str/bytes, structured) stay on stock rather than
   re-proving `zeros`-vs-`copyto` fill equivalence for each.
3. Layout is resolvable: `a` is C-contiguous (route to
   `np.zeros(a.shape, dt, order='C')`) or F-contiguous (route with
   `order='F'`). `order='K'` on a non-contiguous input matches `a`'s
   stride pattern via `empty_like`, which `np.zeros` cannot reproduce -
   fall back to stock there.

Route: `np.zeros(a.shape, dtype=dtype if dtype is not None else a.dtype,
order=<resolved>)`. The result is bit-identical by construction - an
all-zeros base ndarray of the same shape, dtype, and (contiguous) layout -
so correctness risk is low; the risk is entirely in the predicate edges
above.

Semantics hazard that is invisible in values: the fast path returns
lazily-zeroed pages where stock returns touched memory. Values are
identical, but RSS at return time and the location of first-touch cost
differ. That is the same trade `np.zeros` itself already makes, so it is
defensible, but it must be documented, and it is why alloc-only benchmarks
overstate the win.

## What the Dyno reproducer must measure

1. Reproduce the claim regime: alloc-only `zeros_like(a)` vs
   `np.zeros(a.shape)` at `(1000, 1000)` float64 on current numpy, to
   replace the derived 53.56x with a measured, fingerprinted number.
2. Alloc-plus-touch variants: create then fully write (`r[:] = 1`) and
   create then fully read (`r.sum()`), both legs, same sizes. This prices
   the deferred page faults and yields the honest end-to-end ratio; without
   it the record's number cannot be interpreted.
3. Size sweep across the allocator's lazy-zero threshold: e.g. `(100,)`,
   `(100, 100)`, `(1000, 1000)`, `(4000, 4000)`. Below the threshold both
   paths memset and the gap should collapse; the crossover locates the
   minimum size gate for dispatch.
4. Dtype and layout spread: float64/int32/complex128; C- and F-contiguous
   inputs; one non-contiguous slice input and one ndarray-subclass input to
   verify the fallback path stays on stock and stays correct.
5. Correctness assertions per case: result equals stock `zeros_like` in
   values, dtype, shape, order flags, and writeability.
