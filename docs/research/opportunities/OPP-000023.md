# OPP-000023: transparent sort/hash fast path for np.isin on StringDType

Source: numpy/numpy#32161, "PERF: np.isin is very slow for StringDType",
opened by ngoldbaum on 2026-07-31. State at ingestion: open, labels
`01 - Enhancement` and `component: numpy.strings`. The thread has zero
comments; the only activity after the opening post is labeling, a mention of
@ikrommyd, and a cross-reference from draft PR numpy/numpy#32217 on
2026-08-06.

## What is slow

`np.isin` on a StringDType (`dtype='T'`) array takes a fallback path that is
orders of magnitude slower than the sorting path the same data reaches when
cast to fixed-width unicode. The reporter's complete benchmark:

```python
import numpy as np, timeit
a = np.array(['abcd'*5, 'defg'*5, 'abhoj'*6] * 10**4, dtype='T')
print('T:', timeit.timeit(lambda: np.isin(a, a), number=1), 's')
print('U:', timeit.timeit(lambda: np.isin(a.astype('U30'), a.astype('U30')), number=1), 's')
```

On the reporter's laptop (no hardware or numpy version given) this prints:

```
T: 2.9416205829475075 s
U: 0.020494583994150162 s
```

That is a computed ratio of 143.53x (2.9416205829475075 /
0.020494583994150162), and the U timing includes both `astype('U30')` casts
inside the timed lambda, so the real gap between the two internal paths is
somewhat larger than the ratio suggests. The thread's own summary is
qualitative: "So `StringDType` is orders-of-magnitude slower."

The array is 30000 elements holding only 3 distinct strings (lengths 20, 20,
and 30), tested against itself - a low-cardinality, self-membership regime.

## Why (per the thread)

The opening post attributes the gap precisely: this is "more-or-less the
same issue as" numpy/numpy#14997 (the object-array isin complaint),
"because both object arrays and stringdtype fall back to the `hasobject`
path in the `_isin` helper," with a permalink to
`numpy/lib/_arraysetops_impl.py` lines 910-926 at commit 30483388. "This
slow path is much much slower than the sorting path." The hasobject fallback
is a per-test-element comparison loop over the full element array - O(n*m)
kernel invocations - so with a 30000-element test array it does 30000
full-array comparisons where the sorting path does one sort-and-search.

## What a transparent fast path would look like

The reporter's own upstream sketch translates directly into a PyOverdrive
predicate:

- **Predicate:** the call is `np.isin(element, test_elements, ...)` where
  either argument is StringDType, and the dtype instance either has no
  `na_object` or its `na_object` is a string. The reporter: "an easy fix
  ... is to change the predicate in `_is_in` to allow stringdtype to
  use the sorting path if it has no `na_object` or `na_object` is a
  string." Configured nan-like or None-like `na_object` must fall back to
  the stock object path, exactly as he says upstream would have to.
- **Route:** either (a) the sorting path the U cast already reaches - cast
  both arguments to fixed-width unicode wide enough for the longest string,
  call stock isin, return the boolean result - or (b) a hash-based
  membership pass, the reporter's second idea: "implement a hash-based
  `isin` for stringdtype that uses the existing hash-based unique
  infrastructure." The hash route avoids the U-cast's memory hazard (a
  single very long string inflates every element's storage to that width).
  His third idea, HyperLogLog cardinality estimation to pick between
  sorting and hashing (borrowed from numpy/numpy#31969), is a refinement,
  not a prerequisite.
- **Semantics hazards:** `na_object` equality at the fallback boundary
  (missing-data entries are the reason the object path exists); the
  `invert`, `assume_unique`, and `kind` keyword surface of `np.isin` must
  pass through unchanged or trigger fallback; embedded and duplicate
  values must produce the identical boolean array stock produces. When the
  predicate holds (no na_object or string na_object), string equality is
  string equality on every route, so the result should be exactly equal,
  not approximately - correctness validation is a full boolean-array
  comparison against stock.

## What semantics differ

None, when the predicate holds: isin is a membership test and every
candidate route computes the same membership over the same strings, so the
output must be bit-identical to stock. The correctness risk lives entirely
in the routing edges - na_object configurations, the keyword surface, and
making sure the U-cast width is computed from the data rather than assumed.

## Is it common enough to matter

`np.isin` is a core set operation, and StringDType is numpy's own
recommended replacement for object-dtype string arrays, so the collision of
the two is a mainstream path, not a corner. The thread itself, though, names
no downstream user or workload - the demand evidence is that a maintainer
found it worth filing and then worth fixing himself within a week
(PR #32217), plus the long history of the sibling object-array complaint
(numpy/numpy#14997). No corroborating benchmark from a second party exists
in the dump.

## What the Dyno reproducer must measure

1. Replicate the reporter's exact point first: `np.isin(a, a)` on the
   30000-element, 3-unique-string 'T' array versus the same call after
   `astype('U30')`, on a pinned numpy version, to confirm the ~144x gap
   still exists on current numpy (and record whether numpy/numpy#32217 has
   merged into that version - if it has, measure against the release
   before it too).
2. Sweep the regime, because the claim point is a best case for any
   set-based method: cardinality (3, ~100, ~n distinct values), element
   count (1e3 to 1e6), string length (short, mixed, one very long outlier
   to expose the U-cast memory hazard), and disjoint element/test arrays
   of unequal sizes (small test set against large element array is the
   common real-world isin shape).
3. Measure both candidate routes - U-cast-to-sorting-path and a Python/C
   hash-set membership pass - separately, since the winner plausibly flips
   with cardinality and string length; the crossover, if there is one, is
   the predicate an adaptive dispatch needs.
4. Correctness: full boolean-array equality against stock on every case,
   plus explicit probes for a StringDType with a string `na_object`, with
   a nan-like `na_object` (must fall back), and for the `invert=True` and
   `assume_unique=True` keyword paths.
