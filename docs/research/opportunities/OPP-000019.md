# OPP-000019: matmul(out=) page-fault contention with OpenBLAS threads

Source: numpy/numpy#18669, "np.matmul with `out` parameter slower than np.dot
in some cases", opened by bmerry on 2021-03-23. State at ingestion: open,
labels=['57 - Close?']. Retrieved 2026-08-23.

## What is slow

`np.matmul(a, b, out=c)` can be much slower than the semantically equivalent
`np.dot(a, b, out=c)` when `c` is a freshly allocated, not-yet-page-faulted
output array. In the reporter's own repro (1000 batched 1024x32 by 32x1024
complex64 matmuls, C-contiguous, via OpenBLAS): matmul with a cold `out`
buffer ran at 36.0 GFlops, dot at 87.7 GFlops on the same shapes. Once the
output buffer is pre-faulted (touched) before the call, the ranking reverses:
matmul jumps to 213.9 GFlops and dot to 135.7 GFlops, so pre-faulted matmul
ends up faster than pre-faulted dot too.

## Why (per the thread)

bmerry traced the cause directly: `np.dot`'s CBLAS path
(`cblasfuncs.c`) unconditionally `memset`s the output buffer before calling
into CBLAS; `np.matmul`'s path (`matmul.c.src`) does not. bmerry confirmed
this by commenting out the memset call in dot's code path: "Confirmed: if I
comment out that memset, `dot` and `matmul` perform similarly." His working
theory is that OpenBLAS's multiple threads all fault in pages of the cold
output buffer simultaneously and contend on kernel locks during that
faulting, and that dot's upfront memset avoids this by paying the fault cost
serially, single-threaded, before GEMM ever starts.

it should slow down things measurably if its unnecessary and it seems to

the BLAS contract when beta=0, but should probably stay for edge cases: "But
I expect a few code paths may need the memset anyway, which probably is why
its there (i.e. if the inputs have 0-size or if the NumPy slow fallback is
used)."

The reporter himself is the most telling objection: bmerry, 2021-05-11,
after further benchmarking a comment-out patch: "So far the slowdowns are
generally much less significant than the speedups, but we've still only
sampled a tiny part of the multi-dimensional problem space. If you feel that
this is a risky change for dubious reward I would have no objections to
closing the bug."

## Existing projects / PRs that attempted it

No numpy-side PR is linked anywhere in the thread. The only cross-reference
is bmerry's own follow-up bug report against OpenBLAS itself:
https://github.com/xianyi/OpenBLAS/issues/3197, opened to ask whether the
memset/prefault behavior belongs in the BLAS library rather than in numpy.
Its later benchmarking (summarized back into this numpy issue) found the
memset's effect "complicated and system-dependent," sometimes a net loss.

## What semantics differ

None, if implemented as a pure prefault or memset. In a GEMM call with
beta=0, the BLAS contract (quoted by seberg from the reference docs) says
"C need not be set on input," meaning the output buffer is write-only for
this call shape; zeroing or touching it beforehand cannot change the
numeric result, only the timing of when its pages get faulted in. seberg
raised one edge-case concern: if an implementation instead memsets/mutates
the input in a way visible on error paths, "in some cases errors can occur
and then setting random values may be a bit confusing" (referring to a
different design he considered and stepped back from, not the plain-prefault
approach).

## Is it common enough to matter

Narrower than it first looks. The effect requires (a) an `out=` array that
is freshly allocated and not yet touched, (b) a matmul large enough to
dispatch to multi-threaded OpenBLAS, and (c) apparently benefits from
multiple threads specifically (seberg noted the gap shrank, though did not
vanish, under `OMP_NUM_THREADS=1`). Only one shape/dtype was ever swept in
the thread (1024x32 @ 32x1024 complex64, batch of 1000), so there is no
evidence in the dump about how the effect scales with size, dtype, or
thread count beyond that single data point.

## What PyOverdrive should do next

1. Write a Dyno reproducer comparing `np.matmul(a, b, out=c)` against
   `np.matmul(a, b, out=c)` with `c` pre-faulted immediately before the
   call (one write per page, not a full memset, per seberg's own
   suggestion), plus `np.dot(a, b, out=c)` as a reference point. Baseline
   call: `np.matmul(a[i], b[i], out=c[i])` looped per batch index, matching
   the issue's `matmul_loop` mode. Sweep at minimum the reporter's own shape
   (1024x32 @ 32x1024, batch 1000, complex64) plus at least one smaller and
   one larger batch/matrix size, and both complex64 and float64, since the
   dump gives evidence for exactly one dtype and the effect's dependence on
   dtype is unverified.
2. If prefaulting reproduces a real win on current NumPy's OpenBLAS build,
   that is a transparent fast-path candidate: detect a large, freshly
   allocated `out=` array on entry to matmul dispatch and touch its pages
   before handing off to BLAS, with no public API change.
3. Because bmerry's own follow-up benchmarking called the effect "complicated
   and system-dependent" with occasional losses, the reproducer must also
   test across at least two thread-count settings (`OPENBLAS_NUM_THREADS=1`
   and the default) before this record can move past `unverified`, since a
   fast path that only helps at one thread count is a much weaker claim.
4. Track the linked OpenBLAS issue (xianyi/OpenBLAS#3197) for any upstream
   resolution; if OpenBLAS fixes this at the library level, a numpy/PyOverdrive
   -side prefault becomes redundant on updated OpenBLAS builds and the
   fast path should be gated on OpenBLAS version.
5. Given the reporter's own ambivalence and the stale, unresolved state of
   the issue, treat a `not_reproduced` or `rejected` outcome as a fully live
   possibility going in, not a surprise result to explain away.

## Does it reproduce (2026-08-23, fp 8f8198d9abab, numpy 2.4.5, contended box)

Prefaulting the `out=` buffer before `matmul(out=)` is never worse than cold
at large sizes, but the magnitude falls well short of the claimed 5.94x. Best
case, complex64 at the reporter's own shape (1024x32 @ 32x1024, batch 2):
prefaulted 1.92x (5.346 ms -> 2.788 ms); float64 same shape: 1.64x. Batch-8
cases land 1.78x-1.79x for both dtypes. `np.dot` as a reference point trails
prefaulted matmul in every case (1.16x-1.59x) but never loses to cold. At
small size (128x32 @ 32x128, batch 4) the effect REVERSES: both dtypes and
both prefaulted and dot come in slower than cold (0.86x-0.98x). All variants
report correct=True; no correctness failures. Best measured (1.92x) is under
a third of the claimed 5.94x, so this record is stamped `not_reproduced`.
A transparent PyOverdrive fast path (predicate on large, freshly-allocated
`out=` arrays going into threaded-BLAS GEMM, prefault before dispatch) is
not worth shipping on this evidence: the win is modest even where it exists,
reverses at small sizes, and the box was contended, so a clean, uncontended
re-run at the reporter's actual batch=1000 scale would be needed before this
could move off `not_reproduced`.
