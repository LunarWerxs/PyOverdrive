# OPP-000010: sort-kind selection by return_indices, not dtype, on narrow integers

Source: numpy/numpy#16923, "np.intersect1d is several times faster for
return_indices=True", opened by mganahl on 2020-07-21. State at ingestion:
open, retrieved 2026-08-23. This is a bug/behavior report, not a feature
request, and it never received a fix or a linked PR in the fetched data.

## What is slow

`np.intersect1d(a, b, return_indices=False)` is several times slower than
the same call with `return_indices=True`, for narrow integer dtypes. The
reporter's own example: int16 arrays of length D=20000, `return_indices=True`
about 6x faster than `return_indices=False` ("on my computer"). rossbar
traced this to `np.unique`, which `intersect1d` calls internally:
`np.unique(a, return_index=True)` measured at 128 microseconds versus
`np.unique(a, return_index=False)` at 402 microseconds (int16, D=20000, mean
of 7 runs).

## Why (per the thread)

Feelx234 pointed at the actual branch in `arraysetops`: when indices are
requested, the code calls `ar.argsort(kind='mergesort')`; otherwise it calls
plain `ar.sort()` (quicksort by default). charris explained why that matters
for narrow integers: "That is probably because radix sort is now used for
integer types <= 16 bits in stable (nee merge) sort." He backed this with a
raw sort comparison on uint16, size 10000: `np.sort(kind='quicksort')` at
364 microseconds versus `np.sort(kind='stablesort')` at 32.5 microseconds.
So the speed difference between the two `intersect1d` call
shapes is a side effect of which sort NumPy happens to invoke for indexed
versus non-indexed unique, not a deliberate dtype-based choice.

## Who reported and when

mganahl, 2020-07-21. Seven comments followed, from 2020-07-21 through
2020-09-11, from rossbar, Feelx234 (twice), charris (twice, numpy core
dev), hameerabbasi, and sirvincent. The last comment, from Feelx234 on
2020-09-11, pointed to a related assume_sorted proposal (#16964); no
maintainer PR was opened against this issue in the fetched data, and the
issue remains open as of retrieval (2026-08-23), open for over five years
with the diagnosis on record but unshipped.

## Maintainer objections

sirvincent asked: "Might it be a solution to give the user the choose of
the sorting algorithm used by the sorts in intersect1d? Or might this
return erroneous intersect1d output for some algorithms?" charris (numpy
core dev) replied: "That was what we wanted to do, but it requires messing
with the ndarray structure which led to other problems." That is the one
recorded obstacle in this thread, and it targets a *different, larger*
change than what PyOverdrive would ship: sirvincent's ask was a
user-facing sort-algorithm keyword; charris's objection is about the
plumbing that would take. Nothing in the thread objects to the narrower
move of simply defaulting to the already-existing faster internal sort
for narrow integer dtypes regardless of `return_indices`.

## Existing projects / PRs that attempted it

No numpy-internal PR is linked from this issue. hameerabbasi points back
at "the original PR" that benchmarked timsort against radix sort,
referenced via a comment link into numpy/numpy#12586, and says the team
"found that the sweet spot was the transition between 16-bit and 32-bit
integers," offering to revisit the benchmarks. The only cross-referenced
PR in the timeline is external: `google/TensorNetwork#780` ("add unique
and intersect", closed), which merely consumes `unique`/`intersect1d`
downstream and does not touch NumPy's implementation.

## What semantics differ

None, as scoped by PyOverdrive: forcing `kind='mergesort'` for the
internal sort on narrow integer dtypes changes *how* the sorted-unique
result is computed, not *what* it is. `intersect1d`/`unique` output is
already sorted and de-duplicated regardless of sort kind, so a dtype-gated
default change should be bit-identical to the current `return_indices=True`
path's output, applied to the `return_indices=False` path too. The
larger, unshipped idea sirvincent raised (a user-selectable sort-algorithm
keyword) is a different surface and is explicitly the one charris flagged
as running into ndarray-structure complications; PyOverdrive should not
conflate the two.

## Is it common enough to matter

Plausibly, for a narrow but real slice: any code intersecting or
uniquifying int8/uint8/int16/uint16 arrays without requesting indices,
which given `np.unique`'s and `np.intersect1d`'s dtype-agnostic default
behavior likely spans a wide variety of casual callers who never noticed
the flag-dependent speed cliff. The thread gives no usage telemetry or
downstream-project citation for this specific issue (contrast OPP-000007,
where the reporter names pandas explicitly); commonality here is inferred
from the mechanism (any narrow-int unique/intersect call) rather than
demonstrated by the thread.

## What PyOverdrive should do next

1. Write a Dyno reproducer comparing four calls on the same random input
   arrays: `np.unique(a, return_index=False)` (baseline, current default
   sort) against `np.unique(a, return_index=False)` with the internal
   sort forced to `kind='mergesort'` (candidate), and the same pair for
   `np.intersect1d(a, b, return_indices=False)`. Sweep dtypes int8, uint8,
   int16, uint16, int32, uint32 (to locate today's actual radix-sort
   crossover, per hameerabbasi's caution that 16-to-32-bit was the
   sweet spot only "at that time") and sizes 10000, 20000, 100000,
   1000000, at both low-cardinality (values 0-9, matching mganahl's
   repro) and high-cardinality inputs.
2. If the candidate reproduces a meaningful speedup for `return_indices=
   False`/`return_index=False` on the narrow-int dtypes, that is the
   transparent fast path: dtype-gated internal default (itemsize <= 2,
   integer), no new keyword, no output change, so it is a strict
   improvement rather than an opt-in.
3. Confirm bit-identical output against stock NumPy across the swept
   dtypes and both low- and high-cardinality regimes before treating this
   as more than reproduced, since charris's own aside ("Even for floats,
   stablesort may faster on modern hardware... although not on my
   platform") is a reminder that these effects are hardware- and
   compiler-dependent.
4. Cross-check against OPP-000001 (unique hash vs sort) and OPP-000007
   (sorted-set intersect1d): all three touch the same `np.unique`/
   `intersect1d` internals, so a shipped fast path for one should be
   re-verified against the others rather than landed independently.

## Does it reproduce (2026-08-23, fp 8f8198d9abab, numpy 2.4.5, contended box)

Forcing `kind='mergesort'` for itemsize <=2 dtypes (int8/uint8/int16/uint16),
regardless of return_indices, reproduces and then some on high-cardinality
int16/uint16: unique up to 28.0x, intersect1d up to 16.1x, far past
mganahl's informal 6x. On his actual repro shape (int16, D=20000,
low-cardinality/duplicate-heavy 0-9 values), the win shrinks to intersect1d
2.10x / unique 2.12x, well under 6x. int8/uint8 sit around 1.5x-3.0x.
It LOSES outside the 16-bit boundary: int32/uint32 low-cardinality inputs
get 3.4x-4.4x SLOWER (0.23x-0.36x) forced into mergesort, and even
int32/uint32 high-cardinality is a modest 1.9x-4.2x. All 72/72 cases
correct. Evidence: benchmarks/results/OPP-000010/8f8198d9abab.json.

A transparent fast path looks worth shipping, but only under a narrow
predicate: itemsize <= 2 (int8/uint8/int16/uint16) exactly, never widened to
32-bit, since the 32-bit low-cardinality case is a clear regression.
