# OPP-000015: pre-sorted query-array fast path for np.searchsorted

Source: numpy/numpy#10937, "Big speed up in searchsorted if second input is
also sorted", opened by ahwillia on 2018-04-20. State at ingestion: open, no
labels. The thread has nine comments from four commenters (eric-wieser,
charris, ahwillia, juliantaylor), all from 2018-04-20 to 2018-04-21, and
has sat unresolved for over eight years (retrieved 2026-08-23).

## What is slow

`np.searchsorted(x, y)` where `x` (the sorted haystack) is searched for each
element of `y` (the query array), and `y` itself is left in its original,
unsorted order. The reporter's own timing: with `x` and `y` both length
5,000,000 float64 arrays from `np.random.randn`, and `x` already sorted,
`np.searchsorted(x, y)` took Wall time 10.4 s. Sorting `y` first and then
calling the identical `np.searchsorted(x, y)` -- timed together with the
sort -- took Wall time 971 ms, "even taking into account the up front cost
of sorting" the query array.

## Why (per the thread)

charris pointed to the existing C comment on the function: "Updating only
one of the indices based on the previous key gives the search a big boost
when keys are sorted, but slightly slows down things for purely random
ones." He described the mechanism as binary search modified so "the first
trial is the last success rather than the center of the whole array. When
the keys are sorted, the search range decreases as the keys move upwards."
ahwillia pushed back that this should only be a modest win: "I see so unless
I'm missing something this is still a suboptimal speedup -- i.e. it does not
reduce the runtime from `O(n log n)` to `O(n)`." juliantaylor supplied the
mechanism that actually explains the size of the effect: "What is actually
providing the speedup here is the reduction in branch misses. With this
dense list of keys to search the wanted next key is usually very close to
the beginning of the remaining search space so the branch results are
mostly going the same direction."

## Maintainer objections

juliantaylor, on the general "prefer sorted keys" heuristic: "the
optimization of reducing the search space is actually harmful for the
unsorted performance here, we knew these cases exist when it was
implemented, but at the time the binsearch was also untyped so in total the
performance was still better for all cases. It might be worthwhile to tune
this code again a bit for unsorted keys." That is a direct, unresolved
caveat: the same mechanism that helps sorted queries can regress unsorted
ones.

charris, on the size of the effect: "Agreed that the effect is unexpectedly
large, my back of the envelope calculation, which may be way off, gives me
an expected speedup of ~7%." That is roughly 1.5 orders of magnitude below
the ~10.7x the reporter measured, and the gap is never closed in-thread.

eric-wieser, pushing back on the literal `merge_sorted` ask: "Note that a
`merge_sorted(a, b)` implementation would be `O(Na + Nb)`, whereas
search_sorted (without the optimization above is `O(Na log Nb)`. For large
Nb, `search_sorted` is faster than the merge approach." I.e. a dedicated
merge function is not a
strict improvement over `searchsorted` in general, only in some regimes.

## What semantics differ

If implemented as a transparent reordering, none should be observable:
sort a copy of `y`, run `searchsorted` against the sorted copy, then
scatter the result indices back into `y`'s original positions using the
same permutation. Each element's insertion index is independent of the
other query elements, so this does not require a stable sort and should
produce output bit-identical to stock. The risk is not in the output values
but in juliantaylor's caveat above: if the fast path is applied
unconditionally rather than gated on an actual sortedness check (or a real
argsort-then-unpermute transform), unsorted-query workloads could regress
rather than improve, since the underlying binary-search heuristic already
"slightly slows down things for purely random ones" per charris's quoted
code comment.

## Is it common enough to matter

Plausibly, in principle: `searchsorted` against a large, arbitrarily-ordered
query array is a normal shape for binning, histogramming (eric-wieser's own
motivating case), and lookup-table style workflows. But the evidence here is
a single reporter, a single array shape (5,000,000 vs 5,000,000, float64),
and no stated hardware; the ~7% (charris's algorithmic estimate) versus
~10.7x (observed) gap was flagged by a maintainer and never resolved, so the
magnitude -- not just the existence -- of the effect is unverified.

## What PyOverdrive should do next

1. Write the Dyno reproducer. Baseline call:
   `np.searchsorted(x, y)` with `x` pre-sorted and `y` left unsorted.
   Candidate: `perm = np.argsort(y); y_sorted = y[perm];
   idx = np.searchsorted(x, y_sorted); result = np.empty_like(idx);
   result[perm] = idx` (argsort + search + unpermute, timed as one unit,
   matching how the reporter timed sort-then-search together). Sweep sizes
   1e3, 1e4, 1e5, 1e6, 5e6 (the reporter's own point), 1e7 for both `x` and
   `y`, plus at least one size-ratio sweep (e.g. `len(x)` fixed at 1e6 while
   `len(y)` varies 1e3-1e7) to test eric-wieser's "for large Nb,
   search_sorted is faster" caveat. dtypes: float64 (as reported) and
   int64.
2. If the reproducer confirms a meaningful speedup in some regime, treat
   juliantaylor's objection as a hard requirement, not a nice-to-have: the
   fast path must include a real cost/benefit gate (size threshold and/or
   an O(n) monotonicity precheck on `y`, in the style already shipped for
   OPP-000007) so that already-sorted or small `y` never pays unnecessary
   argsort overhead, and unsorted `y` below the threshold stays on stock.
3. If it reproduces, characterize whether the win is the documented
   algorithmic effect (charris's ~7% estimate) or the branch-prediction
   effect juliantaylor proposed, since a branch-prediction-driven win may
   vary substantially across CPU microarchitectures in a way an
   algorithmic win would not; record this uncertainty explicitly in
   `current_numpy_result.detail` rather than treating one reproduction as
   representative of all hardware.
4. Cross-check against OPP-000007's shipped `intersect_sorted` path, which
   already implements the O(n) monotonicity precheck this fast path would
   reuse; prefer sharing that precheck rather than re-deriving it.

## Does it reproduce (2026-08-23, fp 8f8198d9abab, numpy 2.4.5, contended box)

Reproduced, below the claim. At the reporter's own shape (x and y both
5,000,000 float64), argsort_unpermute beat stock np.searchsorted 4790.3 ms
to 650.1 ms, a 7.37x speedup - real, but well short of the reporter's
10.71x, and this run's box was contended (another process was competing
for CPU), so 7.37x is a lower bound, not a clean-hardware number. The
biggest win in the 14-case sweep was equal_n1000000_int64 at 14.47x
(1512.5 ms -> 104.6 ms); float64 at 1e5-1e6 and the size-ratio sweeps with
len(y) >= 1e4 landed 2.17x-2.56x. It loses outright at small or skewed
sizes: equal_n1000_float64 (0.41x), equal_n1000_int64 (0.51x),
equal_n10000_int64 (0.99x, a wash), and ratio_x1000000_y1000_float64
(0.73x, small query against a large haystack) - exactly juliantaylor's
predicted regression for unsorted-adjacent/small query arrays. All 14
cases were correct=true. A transparent PyOverdrive fast path looks worth
shipping, but only gated on a size threshold (roughly len(y) >= 1e4 per
this sweep) plus the OPP-000007-style O(n) monotonicity precheck, never
applied unconditionally.
