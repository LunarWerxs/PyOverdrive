# OPP-000022: partition-vs-sort density cliff in np.quantile / ndarray.partition

Source: numpy/numpy#32187, "BUG: np.quantile / ndarray.partition become much
slower than a full sort once `kth` density crosses ~50%", opened 2026-08-04
by johannfaouzi (author_association CONTRIBUTOR). State at ingestion: open.
Label: `00 - Bug`. Discussion runs 2026-08-04 through 2026-08-05; retrieved
2026-08-24. Provenance note: the issue body opens with "This issue was
written by Claude, but I reviewed it and ran the code," and the root-cause
analysis in the confirming comment is explicitly marked by eendebakpt as
Claude-generated text he posted.

## What is slow

`np.quantile(a, q, axis=-1, method="linear")` becomes dramatically slower
than a naive "sort once, then interpolate" baseline once `len(q)` is a
sizeable fraction of the array length. For linear interpolation, `_quantile`
(`numpy/lib/_function_base_impl.py`) collects a floor and a ceil neighbor
index for every requested quantile and makes one
`arr.partition(np.unique(...), axis=0)` call, so the `kth` array can hold up
to `2*len(q)` distinct entries. Per the body: partition's cost "does not
degrade gracefully as the `kth` array gets denser. Instead there's a sharp
cliff," after which "`partition` is much slower than `ndarray.sort` on the
same array, despite computing a subset of what a full sort would give you
'for free'". Part 2 of the repro isolates `ndarray.partition` alone, no
`np.quantile` involved, and shows the identical threshold.

The one measured table in the thread is eendebakpt's, on (2048, 300)
float64 partitioned along the length-2048 axis, scalar build, unpatched
main: kth spacing 2 (`len(kth)=1024`) takes 496 ms, "21x sort" (implying a
~23.6 ms full sort); at spacing 2 the time scales 47 -> 2672 ms as rows go
1k -> 8k, roughly 4x per doubling, i.e. quadratic. `argpartition` shows the
same cliff. The issue body's own sweep script prints quantile-vs-manual
ratios, but its output is not included in the thread, so 21x
partition-vs-sort is the most concrete number on record.

## Why (per the thread)

From the Claude-generated analysis eendebakpt posted with his
confirmation: the cliff is at "kth spacing < 4 (i.e. once `len(kth)`
exceeds roughly a third of the array length), not at 50%", and
`np.quantile` hits it at `nq/m` of about 0.25 because the linear method
requests two neighboring indices per quantile, halving the effective
spacing. `introselect` (`numpy/_core/src/npysort/selection.cpp`) has a
fast path for `kth - low < 3`: `dumb_select`, an `O(range * (kth - low))`
selection scan intended for interpolating-percentile pairs. "This path
neither partitions the data nor stores pivots." Multi-kth partitions
process sorted kth values left to right, and once consecutive kth values
are less than 4 apart, every kth takes this path, each re-scanning
essentially the whole remaining tail. "The overall partition then degrades
to `O(n^2)` per lane, which matches the observed timings (~4x slowdown per
array-size doubling at spacing 2)."

partition when `len(kth)` is a sizeable fraction of `n`') could still be a
small follow-up win on SIMD hardware".

## Existing fixes in flight

eendebakpt has a branch,
https://github.com/eendebakpt/numpy/tree/fix/partition-dense-kth ("one
condition change in `introselect_` plus threading the already-available
`nkth` argument"), restricting `dumb_select` so dense multi-kth partitions
fall back to quickselect and behave `O(n log n)`. His A/B numbers: spacing
2 goes 496 ms -> 41 ms (21x sort -> 1.7x sort); spacing-2 scaling becomes
linear (7 -> 59 ms); single kth / median pair / 10 percentile pairs are
unchanged within noise; `argpartition` lands at 44 ms (1.4x argsort).
Correctness was "checked against `np.sort` over 8 dtypes, adversarial
inputs (sorted/reverse/constant/duplicates/NaNs), 2-D along both axes, and
`argpartition` consistency." As of retrieval this exists only as a branch;
the issue is open with no linked PR.

## What a transparent fast path looks like

Predicate sketch: intercept `np.quantile` / `np.percentile` when (a) the
input is a float array on a path `_quantile` would partition, and (b) the
number of distinct kth indices the method will request (up to `2*len(q)`
for linear) crosses the density threshold - per the thread, kth spacing
< 4, i.e. roughly `len(kth) > m/4` at the quantile level `nq/m >~ 0.25`
for linear. Below the threshold, stock partition is the right call and the
path must stay off.

Route: one full `np.sort` along the axis, then numpy's own interpolation
arithmetic on the sorted array - replicating `_quantile`'s lerp exactly,
including its gamma >= 0.5 stability rewrite, as OPP-000013's shipped
nanquantile path already does. The reporter's `manual_quantile` baseline is
this route minus the exact-lerp discipline. Order statistics read off a
fully sorted array are by definition those partition would have placed, so
the correctness surface reduces to matching the interpolation bit-for-bit.

Semantics hazards: non-linear `method=` variants request one index per
quantile (different threshold) and different virtual-index formulas;
`weights=` is accepted only for `inverted_cdf`; NaN propagation, `out=`,
`overwrite_input=`, `keepdims`, and tuple `axis` must behave identically.
Routing `ndarray.partition` itself is stricter: a sorted array satisfies
partition's documented guarantee, but bytes in the unspecified regions
would observably differ from stock output - keep the fast path at the
quantile level.

Shelf-life hazard: if eendebakpt's fix merges upstream, the headline win
collapses from ~21x to the residual ~1.7x scalar-vs-SIMD gap at that
shape. The opportunity is largest on currently released numpy (2.3.5 at
report time) and degrades to "small follow-up win" territory afterward -
the thread says so itself.

## Is it common enough to matter

The body argues yes: "any use case requesting a non-trivial fraction of an
array's order statistics at once (many percentiles, an empirical CDF,
quantile binning with a fine grid) can silently cross this threshold, and
nothing about the calling code looks unusual". The reporter hit it in real
profiling work (a quantile-heavy algorithm ported from PyTorch). Against
that: the issue is young (days old at retrieval), has a single confirmer,
and an upstream C++ fix already exists in branch form, so the window for a
PyOverdrive-side win may be one or two numpy releases wide.

## What the Dyno reproducer must measure

1. Partition-level cliff on the numpy actually installed: partition vs
   full sort on (2048, 300) float64 along axis 0, sweeping kth density
   0.05 through 1.00 (the reporter's part 2 grid), locating the cliff and
   confirming (or refuting) spacing < 4. If the cliff is absent, the
   upstream fix has landed and the record's claim must be re-based to the
   residual sort-vs-partition ratio.
2. Quantile-level win: `np.quantile(a, q, axis=-1, method="linear")` vs
   the sort+exact-lerp candidate on (300, 2048) float64, sweeping nq/m
   over {0.05, 0.10, 0.20, 0.24, 0.25, 0.30, 0.50} (the reporter's part 1
   grid) to finally produce the quantile-level ratio table the thread
   never published.
3. Correctness: max abs diff between candidate and stock per case, with
   bit-identical as the target given the exact-lerp route; NaN-bearing
   and constant/duplicate inputs included.
4. Scaling: spacing-2 partition time vs m from 1k to 8k rows to confirm
   (or date) the quadratic regime the thread reports as 47 -> 2672 ms.
5. Threshold calibration for the dispatch predicate: the measured
   crossover density on this hardware, not the thread's remembered one,
   decides where the fast path turns on.
