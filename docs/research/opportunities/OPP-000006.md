# OPP-000006: SLEEF SIMD library for transcendental functions

## What is slow

NumPy's transcendental ufuncs (log, log2, log10, sin, cos, tan, exp, etc.)
get a vectorized path only on x86-64 with AVX512, where NumPy links
against Intel's SVML library. Every other architecture, including
AArch64, falls back to scalar libm: one call per element, no SIMD lanes
used. On SIMD-capable non-x86 hardware this leaves real vector width idle.

## Why, per the thread

Two contributors working on ARM SVE support (yamadafuyuka and
kawakami-k, also authors of the separate SVE PR #22265) prototyped
routing NumPy's transcendental loops through SLEEF, a vectorized math
library with kernels for NEON, SVE, and AVX512 and multiple accuracy
tiers ("u10" means 1.0-ULP accuracy). Measured on a Fujitsu A64FX
(Armv8.2a + SVE) machine, SLEEF combined with SVE intrinsics made log10
about 4x faster than scalar. Expected gain scales with SIMD lane count
N, reduced by Python/dispatch overhead. No exact sizes or dtypes were
given; the only evidence was a graph image, not machine-readable data.

## Who reported it and when

Opened by yamadafuyuka on 2023-01-23. kawakami-k co-authored the
framing: non-x64 CPUs get only scalar libm, and SLEEF's naming
convention eases multi-architecture targeting. NumPy maintainer mattip
and contributor Mousius are the other participants. Last comment
2023-05-19; issue still open (not merged, not closed) as of retrieval
2026-08-23, dormant over three years.

## Maintainer objections

mattip objected early, repeatedly: NumPy was already moving toward its
own "universal intrinsics" (NEP 38) instead of vendoring more
third-party SIMD math libraries, and SLEEF is a different paradigm. He
weighed vendoring cost directly: SLEEF's source tree is about twice
SVML's size, raising whether NumPy would abandon the
universal-intrinsics migration for these functions, and what happens to
prior work (PRs #17587, #18101). Months later Mousius asked whether to
revisit since the universal-intrinsics PR (#23603) had stalled a month,
but noted SLEEF "doesn't handle errors correctly" from an initial look,
i.e. it may not match NumPy's floating-point error (divide-by-zero,
invalid, overflow) semantics. mattip's final comment recommended closing
the issue, stating SLEEF is not the right direction. No maintainer ever
endorsed the approach.

## Existing projects and PRs

yamadafuyuka's prototype branch (`yamadafuyuka/numpy@add_SLEEF`) was
never upstreamed as a PR. PR #22265 (SVE support, same authors) supplied
the SVE intrinsics used alongside SLEEF for the 4x log10 number; it is
referenced in the issue body but not linked via GitHub cross-reference,
so it is noted here rather than in `linked_prs`. numpy/numpy#23603, the
tracked cross-reference, shows the preferred alternative: float64 tan
via NumPy's own universal intrinsics; closed without merging. SVML (PR
#19478) is the precedent already shipped for x86-64 AVX512; the
objection is doing the same again for a second architecture and library.

## Semantics differences

SLEEF ships multiple accuracy tiers (u10/u05/etc.), so a
correctness-preserving integration would need the tier matching NumPy's
existing ULP guarantees, not just the fastest one. Mousius's comment
that SLEEF mishandles errors means floating-point exception behavior
(NaN, over/underflow, invalid-input flagging) may not match libm/SVML
semantics and would need verification before trusting any correctness
claim.

## Is it common enough to matter

Transcendental functions are extremely common, and the underlying gap
(no SIMD path outside x86-64 AVX512) is real and architecture-wide,
covering AArch64/ARM and any platform without SVML. But the specific
claim is narrow: one function (log10), one uncommon machine (A64FX SVE),
one non-reproducible graph, and a patch combining two unmerged
prototypes rather than isolating SLEEF's own contribution.

## What PyOverdrive should do next

Treat this as a signal, not a shippable idea: the 4x number cannot be
isolated from the SVE-intrinsics contribution, was measured on one
uncommon architecture, was never upstreamed, and drew a direct "not the
right direction" from the maintainer with commit authority. PyOverdrive's
reproduction is necessarily a from-scratch measurement on x86-64, so it
cannot verify the AArch64/SVE claim; the baseline run instead establishes
where NumPy's transcendentals already have SIMD coverage (AVX512 via
SVML) versus where they still fall back to scalar libm, the more durable
and portable version of this opportunity.

## Does it reproduce (2026-08-23, fp 8f8198d9abab)

Still unverified, evidence-annotated only: no SLEEF-backed candidate exists
in PyOverdrive yet, so there is nothing to compare against the 4x claim.
The baseline_only run instead measured stock NumPy 2.4.5's per-element
throughput on this x86-64/AVX512 machine (not the AArch64/SVE hardware the
original claim used). At n=1e6, float64: log10 4.31 ns/elem, log 4.21,
log2 5.43, exp 3.29; float32: log10 3.50, log 1.78, log2 3.33, exp 1.47.
At n=1e4 the per-element cost is similar or slightly higher (float64 log10
3.41 ns/elem; float32 log 1.21 ns/elem). This gives a concrete stock-NumPy
floor to beat once a SLEEF or universal-intrinsics candidate is built.
Full data: `benchmarks/results/OPP-000006/8f8198d9abab.json`.
