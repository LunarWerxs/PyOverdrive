# OPP-000001: np.unique hash path vs SIMD sort path

Status: performance_validated, shipped as `unique_sort` / `unique_values_sort`
Sources: numpy/numpy#31969 (open) · Evidence: `benchmarks/results/OPP-000001/`

## What is slow, and why

NumPy 2.x introduced a hash-based unique (`_unique_hash`, PR #26018, a C++
`std::unordered_set`). For fixed-width numeric dtypes at medium-to-large sizes
it loses badly to the SIMD-accelerated sort path (x86-simd-sort): node-based
allocation per insert, cache-hostile bucket chains, and no vectorization,
against an AVX-512 sort that chews contiguous memory.

## Who reported it

rajat315315, 2026-07-11, with in-thread analysis by FreddieWitherden and
ngoldbaum. The drive-by fix PR (#31970) was closed for quality; upstream work
was slated for "this summer" (2026) and has not landed as of ingestion.

## Does it reproduce

Yes, and it is bigger than claimed on this hardware (Zen 4 AVX-512, numpy
2.4.5, fingerprint 8f8198d9abab):

| Regime | Stock | Sort candidate | Speedup |
|---|---:|---:|---:|
| int64, 1M, high cardinality | 585-813 ms | 13-16 ms | 37-55x |
| int32, 1M, high cardinality | 451-957 ms | 6.8-9.5 ms | 66-101x |
| uint32, 1M, high cardinality | 450 ms | 5.5 ms | 82-88x |
| int64, n=64 (smallest measured) | 4.1 us | 2.2 us | 1.8x |
| int64, 1M, cardinality 10-100 | 5.9-10.9 ms | 3.1-9.4 ms | 1.2-2.3x |

The sort path won every measured case for 32/64-bit ints from n=64 up, at
every cardinality. The claim's "hash wins below ~50 elements" is consistent
with our unmeasured-below-64 region.

Counter-evidence that shaped the predicate (this is why we sweep):

- float64: 0.84-1.07x, no reliable win, excluded.
- float32: parity within noise, excluded.
- int16: 0.38-0.46x, int8: 0.14x. Sort LOSES: small value ranges are where
  hashing/counting shines. Excluded, and uint8/uint16 excluded by the same
  range argument pending measurement.

## Maintainer objections, and how we answer them

- "Needs data across cardinality/dtype/size/CPU and the return_* options"
  (hiSandog): our record carries exactly that sweep; the fast path only
  covers the default-argument call, return_* routes fall back to stock.
- "It is cardinality plus sort quality, not size; ARM may differ"
  (FreddieWitherden): correct, and our thresholds are per-fingerprint
  evidence, not universal constants. ARM needs its own Dyno run before any
  claim there. HyperLogLog-style single-pass estimation remains the better
  upstream fix; our dispatch-level reroute is available today.
- "High quality bar" (ngoldbaum): PyOverdrive ships independently; if
  upstream lands the proper fix, our predicate's win disappears and the path
  is retired by measurement, which is the designed lifecycle.

## Semantics

Bit-identical to stock np.unique: sorted unique values, float NaN run
collapsed (the naive candidate FAILS the NaN check by design in the Dyno run;
the shipped path is the nansafe form, currently moot since floats are
excluded). numpy.unique_values guarantees no order, sorted satisfies it.
ndarray subclasses, kwargs, and unsupported dtypes fall back to stock.

## Verdict

Shipped: Gearbox routes numpy.unique / numpy.unique_values for
{int32, int64, uint32, uint64}, size >= 64, default-argument calls, plain
ndarrays. End-to-end via pyoverdrive.enable(): 37-55x on the headline regime.
Differential + property tests: compatibility/differential/. Monitor upstream
(#31969, ikrommyd's work) each re-ingestion; retire when upstream wins.
