# OPP-000007: assume_sorted fast path for sorted-set operations

Source: numpy/numpy#27042, "assume_sorted attribute for efficient/fast Numpy
set operations (intersect, merge etc.)", opened by Zeutschler on 2024-07-25.
State at ingestion: open, no comments, no timeline events recorded. This is a
feature request that has not yet drawn a maintainer response in the fetched
data, not a settled or rejected proposal.

## What is slow

`np.intersect1d(a, b)` and the related `np.isin` / `np.in1d` do not special
case the situation where both inputs are already sorted and unique (true set
semantics). The general implementation concatenates, sorts, and scans, which
is O((n+m) log(n+m)) work even when the caller already knows both arrays are
sorted. When one array is much smaller than the other (a "point query" or
OLAP-style filter against a large sorted index), a merge-style walk or a
binary-search-per-element walk can do the same job in O(n+m) or O(m log n),
skipping the redundant full sort entirely.

## Why (per the thread)

The reporter's rationale is data-processing workloads: row-index or bitmask
intersections against large sorted arrays, repeated many times (OLAP-style
queries, point queries). They argue NumPy's set operations were not written
with this access pattern in mind, and that competing libraries (DuckDB,
Polars, Vaex, DataTable) are winning share partly on exactly this kind of
operation. The issue proposes a new `assume_sorted=True` keyword (analogous
to the existing `assume_unique`) that would switch to a specialized,
sortednp-style merge algorithm.

## Existing projects / PRs that attempted it

- **sortednp** (PyPI, by Frank Sauerburger): the reference implementation
  named in the issue. Implements merge-based intersect/union for sorted
  arrays in C, and is the source of the reporter's own benchmark numbers.
- No numpy-internal PR is linked from this issue (cross-references section
  was empty in the fetched data). `assume_unique` already exists as a
  parameter on `np.intersect1d`/`np.isin`/`np.in1d` today, but it only lets
  the implementation skip an internal de-duplication pass; it does not skip
  the sort, so it is a different (smaller) optimization than what is asked
  for here.

## What semantics differ

A merge-based or searchsorted-based fast path requires both inputs to
already be sorted and (for intersect) unique. If the caller passes an
`assume_sorted=True` array that is not actually sorted, the result is
silently wrong (no error), same risk class as `assume_unique` today. Any
implementation must decide how aggressively to validate this in debug builds
versus trust the caller in release, since a correctness check would erase
the speed win it exists to buy.

## Is it common enough to matter

Plausibly yes for a specific niche: array/dataframe engines and analytical
pipelines that already maintain sorted unique indices (this is exactly
pandas' `Int64Index`/row-label intersection use case, and the reporter
explicitly calls out pandas as a downstream beneficiary). It is less
relevant to generic array code that does not already sort its data, so the
addressable regime is real but narrower than "all set operations."

## Does it reproduce (2026-08-23, fp 8f8198d9abab, numpy 2.4.5)

Half of it, spectacularly. `intersect1d` on sorted unique int64 with a
searchsorted candidate: 8x at 1k x 100, 34.5x at 1e5 x 1e4, 62x at 1e6 x
1e4, 86.4x at 1e6 x 1e5 (564 ms -> 6.5 ms). Even `assume_unique=True` alone
gives 35-39x at 1e6, which exposes the mechanism: stock `intersect1d`
without it calls `unique` on both inputs through its module-internal name,
so it pays the OPP-000001 hash-path tax twice, and patching `numpy.unique`
cannot reach it. The `isin` half does NOT reproduce: the searchsorted
candidate LOSES to `np.isin` at every size (0.13x-0.70x); NumPy's table
method there is already good. Evidence:
`benchmarks/results/OPP-000007/8f8198d9abab.json`.

## Shipped: `intersect_sorted`

Status: performance_validated. `src/pyoverdrive/fastpaths/intersect_sorted.py`
accelerates `np.intersect1d(a, b)` (no keywords) for two plain 1-D arrays of
the same int32/int64/uint32/uint64 dtype, combined size >= 64, with no new
keyword: each input is checked for strict monotonicity in one O(n) pass
(~3% of a sort: 0.38 ms vs 11.4 ms at 1e6), used as-is if already sorted
and unique, otherwise deduplicated with the same sort-based routine
`unique_sort` ships; the smaller set is then binary-searched into the
larger. Result is bit-identical to stock (sorted unique common values, same
dtype); 44 differential tests plus a hypothesis sweep cover every regime
including full-range extremes, reversed, duplicate-heavy, disjoint and
empty inputs, and every fallback route (`assume_unique=`, `return_indices=`,
mixed dtypes, floats, lists, subclasses, 2-D). `isin` is left on stock on
the evidence above. Calibration sweep of the shipped path:
`benchmarks/micro/bench_intersect_calibration.py` ->
`benchmarks/results/INTERSECT-CAL/`.
