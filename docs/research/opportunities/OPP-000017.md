# OPP-000017: BLAS herk fast path for a @ a.H (Hermitian rank-k) operations

Source: numpy/numpy#6951, "Optimization of `a @ a.H` style operations using
BLAS herk routines", opened by jakirkham on 2016-01-06. State at ingestion:
open, no labels, no resolution. Related: numpy/numpy#6794, numpy/numpy#6932.

## What is slow

`a @ a.H` (equivalently `a @ a.conj().T`, `np.dot(a, a.conj().T)`) computes
a Hermitian matrix product through the general BLAS `gemm` path, producing
the full m x m output even though the result is provably Hermitian and
only half of it (plus the diagonal) is independent information. BLAS ships
a dedicated `herk` (Hermitian rank-k update) routine for this case; numpy
does not call it. The real-valued analogue, `a @ a.T` via `syrk`, was
already optimized in PR #6932, referenced in the opening post as "the same
way that was done for `a @ a.T`."

## Why (per the thread)

jakirkham opens by noting `a.H` is not a view (`.conj()` on a complex array
must materialize a new buffer): "So, it cannot be done the same way that
was done for `a @ a.T` ( https://github.com/numpy/numpy/pull/6932 )." Four
API shapes are proposed: (1) a
"transposed-complex" dtype, (2) a function taking `a` plus a conjugate-side
argument, (3) a keyword argument on `dot`, (4) letting `dot` take a single
array argument meaning `A @ A.H`. njsmith frames the motivation directly:
"gemm has options to implicitly conjugate the left and/or right argument
that aren't currently available from numpy, so we'd genuinely be exposing
new speedup opportunities."

## Who reported and when

jakirkham, 2016-01-06, tagging njsmith, charris and argriffing as
previously-interested parties. Discussion runs through 2016-10-12 (a
"any more thoughts on this?" ping that draws no reply), then goes silent
for over five years until rileyjmurray adds a single comment on 2021-12-02.
No maintainer has closed, labeled, or triaged the issue as of retrieval
(2026-08-23).

## Maintainer objections

- **charris**: "Adding an argument to `dot` would not help `@`, which is
  where we are trying to go. OTOH, it does provide a function, if somewhat
  indirectly..."
- **mhvk**, on the new-dtype proposal: "I quite like the
  'transposed-complex' type (`conjugated64` and `conjugated128`?), as it
  would make `conj` a very cheap operation. But it does seem it would imply
  quite a lot of work, between all the ufunc loops, FFTs, etc. There is
  also substantial risk of confusion..."
- **mhvk**, on any signature change to `dot`: "The fact that `np.dot` can
  be overridden by `__numpy_ufunc__` makes me extra wary about allowing one
  to omit its second argument, replacing it with something non-array-like,
  or even introducing additional keywords in its signature. It should
  really continue to look and behave as much as possible like a normal
  `ufunc`, otherwise things are just going to break in unexpected places."
- **ewmoore**, on the single-argument `dot(a)` idea: "It isn't anywhere
  close to obvious what `np.dot(a)` is suppose to do. `np.dot(a, a.T)` is
  very clear. `np.dot(a, a.T, conjugate='right')` is pretty clear."
- **jakirkham**, self-objecting to his own keyword proposal: "I guess I am
  not thrilled with the keyword argument because we then have to ensure we
  handle cases like `np.dot(a, b, conjugate=\"right\")` where `a` and `b`
  are two totally different arrays. This makes the code in
  `cblas_matrixproduct` a bit more complex (more possible bugs) handling
  cases that we don't really benefit from."

None of these reject the herk optimization itself; every objection targets
one specific proposed *signature* for exposing it, and no consensus was
ever reached in the fetched thread.

## Existing projects / PRs that attempted it

- **PR #6932** ("the same way that was done for `a @ a.T`"): the syrk-based
  precedent for the real-symmetric case, named in the opening post as
  already having solved the easier half of this problem.
- **PR #11133**, "WIP: ENH: Matmul as ufunc" (closed): a cross-referenced
  timeline entry; closed and WIP-prefixed, though the thread gives no
  detail on why it stalled.
- No dedicated herk implementation or merged PR is linked in the fetched
  data.

## What semantics differ

`herk` fills only one triangle of the Hermitian result, so a caller
expecting a dense array needs an explicit mirror step stock `a @ a.H`
does not require. `herk`'s accumulation order also differs from `gemm`'s,
so results can differ in the low-order bits, the trade-off `syrk` (PR
#6932) already accepted. mhvk flags a deeper risk: changing `dot`'s
signature interacts with `__numpy_ufunc__` overrides, "things are just
going to break in unexpected places" if it stops looking like a plain ufunc.

## Is it common enough to matter

The thread gives one concrete downstream signal: rileyjmurray (2021) wanted
`a.H @ b` to avoid the extra allocation of `a.conjugate()`, i.e. a
Gram/covariance-matrix computation on tall data, not a generic square
`a @ a.H`. That is narrower and more identifiable than "any Hermitian
product," plausibly common in signal-processing code, but the thread
offers no usage counts or benchmark evidence to size it further.

## What PyOverdrive should do next

1. Write a Dyno reproducer comparing the baseline call `a @ a.conj().T`
   (equivalently `np.dot(a, a.conj().T)`, stock gemm) against a candidate
   calling BLAS `herk` directly (e.g. `scipy.linalg.blas.cherk`/`zherk`,
   filling one triangle and mirroring it). Sweep dtypes `complex64` and
   `complex128`, and two shape families: square `a` at 64, 256, 1024, 4096,
   and tall-and-skinny `a` (e.g. 100000 x 64 and 100000 x 256) to cover
   rileyjmurray's Gram-matrix use case.
2. Because `a.H` is not a view, do not try to auto-detect the pattern from
   the two operands after the fact; that identity link is lost by the time
   `a @ a.H` reaches any dispatch layer. Prototype the fast path as an
   explicit opt-in call (`pyoverdrive.herk(a)` / `pyoverdrive.gram(a)`),
   which sidesteps every maintainer objection above since none touch a
   function outside `np.dot`'s or `np.matmul`'s own signature.
3. If the Dyno run shows a real, verified speedup, decide the triangle
   semantics explicitly (mirror to full dense by default, or expose a
   `full=False` escape hatch) before shipping; the thread flags this as
   genuinely unresolved, not a formality.
4. Cross-check PR #11133 for why the ufunc-based matmul attempt did not
   land, since a future ufunc-based `matmul` could reopen mhvk's
   signature-change objections.

## Does it reproduce (2026-08-23, fp 8f8198d9abab, numpy 2.4.5, contended box)

No herk candidate ran: scipy is not installed in this repo's .venv, and the
reproducer's herk path needs `scipy.linalg.blas.cherk`/`zherk` (numpy has no
public herk/syrk entry point). `HAVE_SCIPY_BLAS` was False, so all 10 cases
(square complex64/complex128 at n=64/256/1024, tall complex64/complex128 at
100000x64 and 100000x256) skipped the candidate and only recorded the
baseline `a @ a.conj().T` / `a.conj().T @ a` surface, from 47.2us at n=64
complex64 up to 205.028ms at the 100000x256 complex128 tall case. Nothing
won and nothing lost, because nothing but the baseline executed. Status
stays `unverified`, `verified_speedup` stays null. A transparent PyOverdrive
fast path is not yet worth shipping on this evidence; it is worth a second
attempt with scipy installed (or a direct CBLAS/LAPACK binding bypassing
scipy) before any predicate can be judged, and only then under the opt-in
`pyoverdrive.herk(a)`-style predicate this record already recommends, not a
transparent `@` interception.
