# OPP-000018: einsum ~20x slower than other libraries (mostly fixed upstream)

Source: numpy/numpy#22604, "how is numpy's `einsum` so much slower than other
libraries?", opened by mattbarrett98 on 2022-11-16.
State at ingestion: closed (2025-11-14). Labels: '57 - Close?', '33 - Question'.

## What is slow

`np.einsum('thd,Thd->thT', x, y)` with `x`, `y` both shape `(1000, 1, 500)`
float64, called with no `optimize` keyword (numpy's default `optimize=False`
path), on numpy 1.21.6: 363 ms +/- 2.21 ms (7 runs, 1 loop each). The same
contraction: `jnp.einsum` 21.2 ms +/- 1.84 ms, `torch.einsum` 14 ms +/- 87.7
us, `tf.einsum` 18.7 ms +/- 109 us, matching the reporter's own headline:
"np.einsum is ~20x slower than other libraries."

## Why (per the thread)

seberg's diagnosis: "NumPy's einsum is written mostly in C, a good chunk of
it should use SIMD (at least SSE2)," contradicting rgommers' initial guess
that the slowdown was a pure-Python implementation gap. Kai-Striega's
profiling (shape `(10000, 1, 500)`, `optimize=True`) confirmed this: "we
spend roughly 91.2% in the C code (with another 6.5% being used to set up
the arrays)." The real gap, per jcmgray, is that torch/jax/tf treat this
contraction as a batched matrix multiply and dispatch straight to BLAS/XLA,
while numpy's einsum (without `optimize=True` routing to tensordot) walks a
naive nested C loop. jcmgray's own third-party `einsum_bmm` library
demonstrated the mechanism on the profiling shape: "it goes from `18sec ->
500ms` for me," and on an extreme many-index tensor-network contraction with
no batch structure: numpy took "Wall time: 11min 31s" against `einsum_bmm`'s
"Wall time: 98.5 ms," which jcmgray called "an almost 7000x speedup." Both of
those comparisons are against the third-party `einsum_bmm` package, not
numpy-vs-numpy.

## Maintainer objections

- rgommers, 2022-11-29: "And I don't think we want to rewrite the whole
  thing in C/C++."
- dgasmith, 2023-03-30: "I have been hesitant of methods like batched GEMM
  in the past in NumPy proper due to the radically different performance
  expectations for something like einsum. For example, I recall
  `np.einsum('i,i->', vector, vector)` for 3-length inner products was used
  heavily in SciPy (?) making `optimal=True` a poor choice for a default."
- seberg, 2023-03-30: "I am surprised matmul scales down well to small
  arrays, although I also see that there may be cases where it is quite a
  lot slower because it either fails to call out to blas, or tries too hard
  (requiring buffering or so)."
- jcmgray, 2023-03-30, affirming the resulting design constraint rather than
  objecting: "agreed on keeping `optimize=False` as the default to
  prioritize low-overhead small contractions."

## Existing projects

- **einsum_bmm** (jcmgray, github.com/jcmgray/einsum_bmm): third-party
  pure-Python einsum reimplementation via batched matmul; author reports
  "100 to even 1000x" faster "in certain cases I am interested in (large and
  high dimensional tensors)," with the caveat "for small tensors the current
  numpy c_einsum is still very low overhead and slightly faster."
- **opt_einsum** (dgasmith/opt_einsum), raised by charris: "Much of einsum
  _is_ in C."

## PRs that attempted it

- **numpy/numpy#23513**, "ENH: speed up einsum with optimize using batched
  matmul" (jcmgray), opened 2023-03-31, merged. jcmgray's 2025-11-13
  follow-up confirms the fix on the original shape (float32): numpy
  `optimize=True` 2.4 ms +/- 269 us vs torch 1.55 ms +/- 264 us.
- **scipy/scipy#20950**, "ENH: spatial: speed up `Rotation.apply` by
  replacing `np.einsum` with `np.matmul`", cross-referenced from the
  timeline: a downstream consumer working around slow einsum by switching
  to matmul directly.
- **numpy/numpy#30171**, "ENH: add a `use_blas=bool` kwarg to einsum",
  cross-referenced as open: a follow-up proposing an explicit BLAS opt-in
  beyond what #23513 shipped.

## What semantics differ

#23513's batched-matmul path only activates when the caller passes
`optimize=True`; the default stays `optimize=False` specifically to protect
low-overhead small contractions (dgasmith's `np.einsum('i,i->', vector,
vector)` example, and jcmgray's agreement above). A caller who does not pass
`optimize=True`, which is exactly the call in the original bug report, still
takes the slower path today. Routing through BLAS matmul also changes
floating-point summation order versus the naive C accumulation loop, so
results should be treated as equal within tolerance, not bit-identical; this
is a general property of BLAS-substitution changes and was not discussed
directly in this thread.

## Is it common enough to matter

The reported shape, two operands with one small batch-like singleton
dimension contracting to a batched matmul, is exactly what torch/jax/tf
treat as a hot path by default, so anyone porting code between frameworks or
writing new numpy code with einsum's defaults hits this gap without doing
anything unusual. The thread produced one reproducer shape from the original
reporter plus one extreme tensor-network case from jcmgray (motivated by
quantum-computing/tensor-network use, per rgommers' pointers to cuQuantum,
qutip, Qiskit, and pyquil); no maintainer or reporter supplied usage-
frequency data specifically for the default-`optimize=False`,
batch-matmul-shaped case.

## What PyOverdrive should do next

1. Write a Dyno reproducer comparing baseline `np.einsum('thd,Thd->thT', x,
   y)` with no `optimize` kwarg against candidates `np.einsum(..., optimize=
   True)` (the post-#23513 BLAS path) and a hand-written `np.matmul`
   equivalent, sweeping shapes `(1000, 1, 500)` and `(10000, 1, 500)` for
   both operands (the two shapes actually used in the thread) at dtypes
   float32 and float64, plus a small-contraction control case
   `np.einsum('i,i->', v, v)` for `v` of length 3 and length 100 to check
   whether dgasmith's small-array-overhead objection still holds on current
   numpy.
2. If `optimize=False` still trails `optimize=True`/matmul by a wide,
   size-dependent margin on current numpy, that is the transparent fast
   path PyOverdrive is built for: cheaply detect a two-operand einsum
   expression that reduces to a batched matmul (at most one contracted
   axis, at most one batch axis, no repeated-index diagonal/trace),
   size-gate it above whatever threshold step 1's small-contraction sweep
   finds necessary, and silently route through matmul/tensordot without a
   new keyword, the same no-new-API shape already shipped for OPP-000007's
   `intersect_sorted`.
3. Validate correctness against a numeric tolerance rather than bit-
   identity, since BLAS reduction order differs from the naive C loop;
   reuse whatever tolerance convention OPP-000002's tensordot work
   establishes rather than inventing a new one.
4. Track numpy/numpy#30171 (`use_blas` kwarg, open at retrieval) so that if
   numpy ships an official opt-in first, PyOverdrive's threshold and
   semantics stay consistent with it rather than diverging.

## Does it reproduce (2026-08-23, fp 8f8198d9abab, numpy 2.4.5, contended box)

Yes, on the regime the claim is actually about. Original bug shape
(t=1000,h=1,d=500,float64): stock `einsum(optimize=False)` 128.4 ms, a
matmul-routed fast path 3.84 ms (33.5x), bare `optimize=True` 17.6x (7.28
ms). At t=2000,h=1,d=500,float32 the matmul path peaks at 45.0x (255.9 ms
-> 5.68 ms). All four batched-matmul cases land at or above the claimed
~20x. It loses on small classic inner-product contractions, exactly
dgasmith's named counter-case: `optimize=True` alone is 5.6x-6.7x SLOWER
than stock einsum at len=3/len=100, though the matmul-specific candidate
still edges out a small win there (1.52x/2.19x, near the noise floor).
A transparent PyOverdrive fast path looks worth shipping, but only if it
detects the batched-matmul shape specifically (at most one contracted axis,
at most one batch axis) and routes through matmul/tensordot directly,
never by flipping on generic `optimize=True`, which is the predicate
that avoids dgasmith's small-contraction regression while still capturing
the 33x-45x win on the real batched case.
