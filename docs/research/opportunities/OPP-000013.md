# OPP-000013: nanquantile axis-reduction overhead

Source: numpy/numpy#16575, "nanquantile is hundreds of times slower than
quantile for certain cases", opened by ashaffer on 2020-06-11. State at
ingestion: open, label `component: numpy.lib`, with comments spanning 2020
through late 2025 and no PR from numpy's side as of retrieval (2026-08-23).

## What is slow

`np.nanquantile(a, q, axis=...)` is much slower than `np.quantile(a, q,
axis=...)` when the array is 2-D+ and the call reduces along a non-trivial
axis, producing many small 1-D slices. Reporter's repro:

```python
a = np.random.uniform(size=(27, 100))
%timeit np.quantile(a, 0.8, axis=0)      # 147 us +/- 11.4 us
%timeit np.nanquantile(a, 0.8, axis=0)   # 10.3 ms +/- 953 us
```

10300/147 = 70.07x. The reporter notes the two functions are "identical" in
speed for a 1-D vector or for a 2-D array reduced as a whole; the gap is
specific to reducing along one axis of a 2-D+ array.

## Why (per the thread)

seberg (2020-06-12): "the reason is that these are functions written in
Python. They should be fairly efficient on 1-D slices, but will have quite
significant overheads associated to each individual slice... For
`np.quantile` speficially, it is itself implemented in Python to significantly
reduce the overheads in this case, it would probably be required to move
this to C." `quantile` amortizes per-slice call overhead across an axis
reduction; `nanquantile` does not, because each slice can carry a different
count of valid (non-NaN) elements. seberg adds: "There may be small
performance improvements which are easier though (and e.g. general
small-array performance improvements could have a large impact here)."

## Who reported and when

ashaffer, 2020-06-11, numpy 1.18.5 / Python 3.6.4, toolchain string implying
macOS. Comment activity is sparse, spread over 2020-2025; no numpy-side PR.

## Maintainer objections

- seberg (2020-06-12): root-cause quoted above; also "We do not have a good
  solution for this at the time" - not a rejection, an admission of no fix.
- mdhaber (2025-10-23), declining a suggestion he write a fix: "Thanks, but
  I'd rather not get involved... I am not a fan of overloading the meaning
  of `nan`s, so I think that array API compatible masked arrays (e.g.
  [`marray`](https://mdhaber.github.io/marray/tutorial.html))
  are the better alternative to `nan`-flavored functions and `nan_policy`
  arguments. I'd rather not spend time making `nanquantile` less worse... if
  obvious issues like this encourage users to make the change away from
  nanquantile and such, I think it's for the better in the long term." An
  explicit preference to leave `nanquantile` slow as a nudge toward masked
  arrays, not a technical objection to any specific fix.
- cakedev0 (2025-10-24), in response: "That and the fact that the impact of
  this issue is really not big. The slowdown compared to `quantile` is only
  significant when the number of reductions is greater than the size of the
  reduced dimension, which isn't the common use case I think."

## Existing projects / PRs that attempted it

- **fastnanquantile** (PyPI, lbferreira, 2024-01-08), a Numba-JIT
  reimplementation. Their numbers, `np.random.random((50, 100, 100))`,
  `q=0.6`, `axis=0`: stock `nanquantile` 0.2658s vs `fnq.nanquantile`
  0.0099s, a 26.85x ratio (their own disclaimer: first call pays Numba
  compile time).
- **numbagg** (max-sixty, 2023-12-20) ships a `nanquantile`: "slightly
  slower than numpy's on a 1D array, but 5x faster on 2D arrays where
  parallelization is possible."
- carlosgmartin (2021-03-17) references an external workaround blog post,
  "resulting in a 160x speedup" per that commenter's characterization - a
  secondhand claim, not a number confirmed in this thread.
- **numpy/numpy#30066** (open) is the one cross-referenced PR, but it fixes
  a weighted-quantile broadcasting bug, not this performance gap.
- cakedev0 (2025-10-23) offered to port scipy's `nan_policy="omit"`
  quantile implementation into numpy; mdhaber declined (quoted above), and
  no PR followed in the fetched data.

## What semantics differ

None of the candidates change `nanquantile`'s contract; they reimplement
the same NaN-skip-and-interpolate semantics faster. The risk is
implementation correctness: a vectorized masked reduction must reproduce
numpy's interpolation behavior (`method`, ties, all-NaN slices returning
NaN with a warning) for a variable count of valid elements per slice,
nontrivial to make bit-identical to the current Python-loop implementation.

## Is it common enough to matter

Mixed. Against: cakedev0's read that the slow regime only bites when "the
number of reductions is greater than the size of the reduced dimension,"
called uncommon, plus mdhaber's preference to deprecate `nanquantile`-style
functions rather than invest in them. For: repeated independent demand in
the cross-references - two xarray issues on slow skipna quantile
reductions, a bottleneck request to add `nanquantile`, a pythran request
for `nanpercentile`, and numbagg already shipping a faster `nanquantile`.

## What PyOverdrive should do next

1. Write the Dyno reproducer comparing `np.nanquantile(a, q, axis=0)`
   (baseline) against `np.quantile(a, q, axis=0)` on the same array with
   zero NaNs (candidate route 1: skip-to-quantile), and separately against
   a masked/vectorized nanquantile candidate (route 2, arrays that do
   contain NaNs); sweep shapes `(27, 100)` and `(50, 100, 100)` (the shapes
   named in the thread) plus one larger shape, e.g. `(1000, 1000)`, dtype
   float64, q in {0.6, 0.8} to match the thread, and NaN fractions of 0%,
   1%, 10% per slice to separate the two routes.
2. If route 1 reproduces near the reporter's 70.07x on the all-finite case,
   that is the transparent fast path: an O(n) `isnan(a).any()` predicate
   over the whole array, routing to `np.quantile`'s existing fast path with
   no API change and a bit-identical result by construction.
3. Only if route 1 alone is judged too narrow, evaluate the harder masked-
   reduction candidate (fastnanquantile/numbagg-style) for the NaN-present
   case, stress-testing it against numpy's `method=` variants and all-NaN-
   slice behavior before trusting any speedup number.
4. Track numpy/numpy#30066 in case it touches this code path and changes
   the baseline to reproduce against.
5. Re-check this record if #16575 gets new comments, since mdhaber's
   2025-10-23 objection is recent and could still turn into a numpy-side PR
   that changes what PyOverdrive needs to ship.

## Does it reproduce (2026-08-23, fp 8f8198d9abab, numpy 2.4.5, contended box)

Yes, reproduced. 17 cases, every variant correct=true, no losses anywhere.
Claim regime (27, 100), the reporter's own shape: skip_to_quantile (0% NaN,
routes straight to np.quantile) and masked_route2 (1%/10% NaN) land
52.99x-70.35x (q=0.6 nan10%: 2.554 ms -> 36.3 us, 70.35x), bracketing the
claimed 70.07x closely. It scales up further on the larger (50, 100, 100)
shape, best case masked_route2 at q=0.8 nan10%: 397.36 ms -> 3.88 ms,
102.29x; skip_to_quantile there is 44.26x-44.77x. It shrinks on (500, 500),
a fewer/larger-slice shape outside the claim's many-small-slice regime:
5.35x-9.87x (q=0.8 nan0%: 17.86 ms -> 3.34 ms, 5.35x), still a clean win,
never negative. Run was contended (cpu_busy_before 0.37, cpu_busy_after
0.42) so treat the absolute ns as noisy; the ratios track the claim
regardless. A transparent PyOverdrive fast path looks worth shipping: the
0%-NaN case is a bit-identical reroute to np.quantile (zero semantic risk),
and even the harder masked-NaN route stays a solid win everywhere tested,
so the ship predicate is "reduction count exceeds reduced-dimension size"
per cakedev0's mechanism, not the raw array shape.
