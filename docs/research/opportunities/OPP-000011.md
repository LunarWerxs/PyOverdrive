# OPP-000011: 3-multiply (Gauss) trick for complex matmul

Source: numpy/numpy#13229, "Complex matmul is very slow (and here's a 2x
speedup)", opened by Saluev on 2019-03-31. State at ingestion: open, labels
`component: numpy.linalg`, `component: numpy._core`, `28 - Benchmark`.
Retrieved 2026-08-23.

## What is slow

`A @ B` for two complex128 matrices computed the direct way pays for four
real matrix multiplications worth of floating-point work (the naive
expansion of complex multiply-accumulate). The reporter's benchmark, on
numpy 1.13.1 with `(m, n, k) = (2048, 4096, 2048)` complex128 matrices,
measured `A @ B` at wall time 7.45 s (CPU total 13.9 s).

## Why (per the thread)

The reporter proposes the classical 3-multiply (Gauss) complex-multiplication
trick applied to matmul:

```python
C1 = A.real @ B.real
C2 = A.imag @ B.imag
C3 = (A.real + A.imag) @ (B.real + B.imag)
C = (C1 - C2) + 1j * (C3 - C1 - C2)
```

This trades 4 real matmuls for 3 plus O(mn + nk + mk) elementwise
adds/subtracts, cutting the multiply-heavy work by the 25% the title refers
to as "saving 25% of the floating point multiplications." On the same
shapes the reporter measured this at wall time 3.37 s (CPU total 7.57 s),
a 7.45/3.37 = 2.21x wall-time ratio. They also ran their own correctness
check: `np.linalg.norm(C - A@B) / np.linalg.norm(A@B) = 3.9738720532213243e-16`.

A second run, on numpy 1.16.2 (via a hack, since that version reportedly
hung on the direct approach), narrowed the gap sharply: wall time 2.28 s
(`A @ B`) versus 2.09 s (the trick), about 1.09x. The reporter notes this
themselves: "The difference is much smaller indeed."

## Existing projects / PRs that attempted it

None named in the thread. No numpy-internal PR is linked or referenced.
The technique itself (3-multiply / Gauss complex multiplication, aka a
Karatsuba-style trick) is a well-known general algorithm, not something
attributed to a specific third-party library here.

## What semantics differ

The 3-multiply reformulation is not the same arithmetic as direct complex
multiply-accumulate: it introduces an extra subtraction
(`C3 - C1 - C2`) that direct complex multiplication does not have, so
results are not bit-identical to stock `matmul`, only numerically close.
The reporter's single-sample check (3.97e-16 relative error) is reassuring
but is one random-uniform input, not a sweep; Karatsuba-style
reformulations are known to have a worse (though usually still small)
rounding-error profile than direct multiply-add, particularly when the
real and imaginary parts differ greatly in magnitude, since the extra
subtraction can lose relative precision. Any implementation needs its own
error-bound sweep, including magnitude-skewed inputs and NaN/Inf.

## Is it common enough to matter

Complex matmul itself is a real, if narrower, numeric-Python workload
(signal processing, quantum simulation, FFT-adjacent pipelines). But the
thread's own evidence undercuts how stable the win is: the reporter's two
own measurements, taken months apart on different numpy versions with the
identical shape, disagree by a factor of two (2.21x vs 1.09x), and mattip's
opening question about whether this still replicates after the gufunc
rewrite of matmul was never answered. A second sub-thread folded into this
issue (rgommers relaying pj1989's report, later cross-referenced to the
now-closed numpy/numpy#17810) documents a related but distinct problem:
`A.real @ B` where `A.real` is a non-contiguous view into a complex128
array can be up to roughly 120x slower than `A.real.copy() @ B` per
pj1989's own numbers, which is a copy/contiguity issue rather than the
3-multiply trick.

## What PyOverdrive should do next

1. Write the Dyno reproducer: baseline `A @ B` via NumPy's stock
   `numpy.matmul` (`@`) against a candidate implementing
   `C1 = A.real @ B.real; C2 = A.imag @ B.imag;
   C3 = (A.real + A.imag) @ (B.real + B.imag);
   C = (C1 - C2) + 1j * (C3 - C1 - C2)`, both on freshly generated
   `dtype=complex128` (and `complex64`) matrices. Sweep square and
   rectangular shapes bracketing the reporter's own
   `(m, n, k) = (2048, 4096, 2048)`, e.g. `256`, `512`, `1024`, `2048`,
   `4096` per dimension, on current NumPy, to see whether the 2.21x (older
   numpy) or the 1.09x (numpy 1.16.2) result is closer to today's reality
   given mattip's still-unanswered "does this replicate" question.
2. Sweep magnitude-skewed and edge-case inputs (real part orders of
   magnitude larger than imaginary, near-zero components, NaN/Inf) to
   bound the relative error of the 3-multiply path against stock, since
   the only correctness evidence in the issue is a single 3.97e-16 sample.
3. If a real speedup and an acceptable error bound both reproduce, that is
   the shape PyOverdrive's dispatch is built for: detect
   `dtype in {complex64, complex128}`, `ndim >= 2`, and a contracted
   dimension large enough to amortize the extra adds, and route to the
   3-multiply path transparently, with results checked against a
   relative-error tolerance rather than bit-identical equality.
4. Separately scope (or fold into a distinct opportunity) the
   `.real`/`.imag` non-contiguous-view slowness raised by pj1989/rgommers
   and cross-referenced to numpy/numpy#17810; it is a different mechanism
   (copy/contiguity cost, not the multiplication-count trick) and should
   not be conflated with this record's speedup claim.
5. Track mattip's and seberg's open questions (does it still replicate
   post-gufunc rewrite; is the win mostly about out-of-cache array size
   and blocked iteration) explicitly in the reproducer's output so this
   record's `status` can move off `unverified` with an answer to both.

## Does it reproduce (2026-08-23, fp 8f8198d9abab, numpy 2.4.5, contended box)

Not reproduced. The gauss3 3-multiply candidate lost to stock numpy.matmul
on every practically-sized case: complex128 and complex64, 256^3 through
4096^3, and the reporter's own (2048,4096,2048) shape, which scored 0.62x
(207.6 ms baseline vs 335.2 ms candidate) against a claimed 2.21x. The
closest-to-break-even practical result was square_4096 at 0.77-0.78x for
both dtypes, still a loss. Worst loss was square_256_complex64 at 0.24x
(gauss3 ~4.2x slower). Only two microsecond-scale 64x64x64 edge cases
(magnitude-skew and near-zero inputs) nudged above 1.0x, at 1.28x and
1.03x, small and noisy enough on a contended box to read as measurement
noise rather than a real win. All 12 cases were correct, so the technique
is numerically sound, just not fast on current numpy. This matches the
thread's own warning sign: the reporter's second run (numpy 1.16.2) had
already shrunk 2.21x to ~1.09x, and modern BLAS-backed complex matmul has
apparently closed the gap entirely. A transparent PyOverdrive fast path
here is not worth shipping; there is no size or dtype regime in this
sweep where the mechanism wins by a margin that survives noise.
