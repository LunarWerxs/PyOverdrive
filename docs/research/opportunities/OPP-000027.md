# OPP-000027: real-by-complex np.dot is the one slow pairing of the four

Source: numpy/numpy#10468, "A.dot(B) very slow for A real and B complex",
opened by dbstein on 2018-01-25. State at ingestion: open. No labels, no
assignees, one comment (seberg, MEMBER, 2018-01-26), zero reactions, no
recorded activity after 2018-01-26. Retrieved 2026-08-24.

## What is slow

`A.dot(B)` where A is real float64 and B is complex128. The reporter:
"`A.dot(B)` is very slow for the case of A real and B complex (10-50x
compared to A real/B real, A complex/B complex, and A complex/B real). The
behavior persists across different installations on different operating
systems with different BLAS/LAPACK setups."

The repro is a matrix-vector product: A a (10000, 1000) complex matrix, B a
(1000,) complex vector, with `Ar = A.real.copy()` and `Br = B.real.copy()`,
timing all four pairings. Per-loop results, in the order Ar.dot(Br) /
A.dot(Br) / A.dot(B) / Ar.dot(B):

- Reporter, 2 core laptop, "MAC OSX 10.12.6", Python 2.7.14 (Anaconda),
  numpy 1.14.0 on Accelerate: 5.01 / 18.8 / 18.8 / 116 ms.
- Reporter, 16 core machine, CentOS 7.4.1708, Python 2.7.14 (Intel
  Corporation), numpy 1.13.3 on Intel MKL: 1.29 / 2.41 / 2.54 / 110 ms.
- seberg (machine unspecified): 2.57 / 5.54 / 5.54 / 23.2 ms.

Derived ratios (ours; the thread's only stated range is "10-50x"): on the
MKL box the slow case is 85.27x the real-real product and 43.31x the
complex-complex product; on the Mac, 23.15x and 6.17x; on seberg's box,
9.03x and 4.19x. The corpus record carries 43.31 (110 / 2.54, both numbers
the reporter's own) as the claim figure.

Note the asymmetry all three measurement sets agree on: complex.dot(real)
(`A.dot(Br)`) is about as fast as the all-complex product. Only
real.dot(complex) (`Ar.dot(B)`) is slow - the direction where the operand
that would need upcasting is the large matrix, not the small vector.

## Why (per the thread, which is thin here)

The thread never names the mechanism. The only diagnostic contribution is
seberg's, who timed the ingredients of the obvious workaround on his box:
`A.astype(np.complex128)` 23.1 ms, `Ac[...] = A` (assignment into a
preallocated complex array) 12 ms, against his 23.2 ms slow case and
5.54 ms complex dot. His conclusion is about the cast, not the dot: "I am
a bit surprised the casting is that much slower though, sounds like there
might be some performance bug, since it also seems like caching can't
fully explain it away I think."

What the numbers imply but the thread does not establish: on seberg's box
astype-then-dot (28.6 ms) would actually lose to the slow path (23.2 ms),
while assign-then-dot (17.5 ms) wins only modestly; on the reporter's MKL
box the slow path (110 ms) is so far above any plausible upcast-plus-ZGEMV
total that numpy is very likely not reaching BLAS at all for the mixed
real-left case, instead running a buffered non-BLAS fallback loop. The
Dyno work must confirm this on current numpy by profiling, not assume it
from 2018 timings.

## Maintainer objections

None against fixing it. seberg's sole comment (quoted above) treats the
slow casting itself as a possible performance bug. No one argues the
current behavior is intended, and no one proposes an API change - which is
favorable for a transparent fast path: the contract is not in dispute.

## What a transparent fast path would look like

Predicate sketch: `np.dot` (and its method form) where one operand is real
float (float32/float64) and the other is complex (complex64/complex128),
both 1-D or 2-D, the complex operand C-contiguous (or cheaply copyable),
and sizes above a calibrated floor. The thread only demonstrates the
real-left direction as slow; the reproducer should measure both directions
before deciding whether the predicate needs both.

Route, preferred candidate: reinterpret rather than upcast. A contiguous
complex128 array's buffer is interleaved (re, im) float64 pairs, so
`B.view(np.float64).reshape(m, 2)` turns the thread's (1000,) complex
vector into an (m, 2) real matrix with zero copies. Then
`Ar.dot(B) == (Ar @ Bv).view(np.complex128).reshape(n)`: one real DGEMM on
(n, m) x (m, 2), no complex arithmetic, no 80 MB upcast of the matrix,
roughly 2x the real-real work. Against the thread's MKL numbers that
predicts about 2.6 ms versus 110 ms. Fallback candidate: plain
upcast-then-complex-dot, which the thread itself prices at 43.31x with the
upcast excluded, and which seberg's numbers warn can be cast-cost-dominated
on some machines.

Semantics hazards to differential-test: (1) summation order differs from
whatever loop stock numpy uses for the mixed case, so results are
tolerance-equal, not bit-equal - the same class of difference numpy already
exhibits between its own BLAS and non-BLAS paths; (2) sign-of-zero and
NaN/inf propagation, since eliminating the implicit zero imaginary part
removes `0 * x` terms that can manufacture NaNs or signed zeros in the
upcast formulation; (3) mixed-precision pairings (float64 with complex64,
float32 with complex128) must reproduce numpy's promotion table exactly,
which may force a cast of the complex operand and change the economics;
(4) non-contiguous complex operands (e.g. `.imag` views, sliced columns)
cannot be reinterpreted without a copy; (5) `out=` and 2-D result layout
must match stock.

## What the Dyno reproducer must measure

1. Re-establish the baseline on current numpy: all four dtype pairings on
   the reporter's exact shapes ((10000, 1000) x (1000,)), since every
   number in the thread is from numpy 1.13.3/1.14.0 under Python 2.7 and
   the gap may have narrowed or closed. If the slow case is gone, the
   record moves to not_reproduced and stops here.
2. Profile which path stock numpy takes for real-by-complex (BLAS or
   buffered fallback), settling the mechanism question the thread left
   open.
3. Sweep both directions (real.dot(complex) and complex.dot(real)), both
   GEMV and GEMM shapes, float64/complex128 and float32/complex64 pairs,
   and a size ladder, to find the crossover floor for the predicate.
4. Race the two candidates - view-as-(m, 2)-real DGEMM versus
   upcast-then-ZGEMM - against stock, since seberg's numbers show the
   upcast route is not a guaranteed win.
5. Differential-correctness battery: tolerance bounds versus stock,
   NaN/inf/signed-zero probes, non-contiguous operands, `out=`, and the
   promotion table for every mixed pair the predicate admits.
