# OPP-000026: np.mean axis-reduction with tiny trailing axis

Source: numpy/numpy#8480, "np.mean with axis parameter is slower than naive
implementation", opened by gongbudaizhe on 2017-01-16. State at ingestion:
open, label `component: numpy._core`, 3 comments (all 2017-02-19), no linked
PR in the fetched data. Retrieved 2026-08-24.

## What is slow

Reducing over the large axes of an image-shaped array while keeping a tiny
trailing axis is slower than just computing a full mean per trailing slice.
Reporter's repro, verbatim (python 2.7.13, numpy 1.11.3):

```python
import numpy as np
img = np.random.rand(1000, 1000, 3)

np.mean(img, axis=(0, 1))
# 100 loops, best of 3: 12.5 ms per loop

[np.mean(img[:,:,0]), np.mean(img[:,:,1]), np.mean(img[:,:,2])]
# 100 loops, best of 3: 4.42 ms per loop
```

12.5 / 4.42 = 2.83x, derived from the reporter's own two timings; no one in
the thread states a ratio. eric-wieser adds that the equivalent 2-D form is
"Also just as slow":

```python
np.mean(img.reshape(-1,3), axis=0)
```

so the regime is not multi-axis reduction per se, but any reduction over
many rows that leaves a very small non-reduced inner dimension.

## Why (per the thread)

seberg (2017-02-19), the only root-cause analysis given: "The problem is
probably that it is actually much much faster in the case of img.shape[2]
being large and that path is always taken preferred (because of better
memory order). In the case of img.shape[2] being small, it makes the inner
loop small though, making the iteration itself less efficient. In that case
avoiding memory layout iteration reordering could make sense."

Mechanism in short: `ufunc.reduce` reorders iteration to follow memory
order, which wins when the kept trailing axis is large (long contiguous
inner loops) and loses when it is tiny (length-3 inner loops, so
per-iteration overhead dominates). The per-slice baseline instead runs
three full contiguous reductions, each with a long inner loop.

eric-wieser (2017-02-19) broadens the scope: "This applies to np.sum and
np.add.reduce as well. I think in general, the problem lies in
np.ufunc.reduce. By comparison, einsum performs way better" (no einsum
number is given).

## What a transparent fast path would look like

- Predicate: a mean/sum/add.reduce call whose reduction leaves only a
  small trailing axis (length below a calibrated threshold; the thread's
  case is 3) on a C-contiguous float array, with the reduced extent large.
  Per seberg the same code path is "much much faster" when the trailing
  axis is large, so the predicate must keep large-trailing-axis calls on
  stock numpy untouched.
- Route: compute one full contiguous reduction per trailing slice (the
  reporter's own candidate), or equivalently a reshape(-1, k) followed by
  an einsum/dot-based column sum divided by the row count (eric-wieser's
  faster-still observation), then assemble the length-k result.
- Semantics hazards: the reroute changes floating-point summation order
  relative to stock numpy's pairwise-summation traversal, so results are
  numerically close but not guaranteed bit-identical - this is the main
  correctness question the differential tests must bound. NaN/inf
  propagation, dtype promotion, and the returned shape/dtype are
  unchanged. keepdims, out=, where=, and dtype= arguments either need
  handling or must fail the predicate and fall back to stock.

## Is it common enough to matter

The measured shape is the canonical RGB-image mean (H, W, 3) - channel-wise
statistics over images are an extremely common numpy workload, and the 2-D
form reshape(-1, k) with small k covers per-feature means over tall skinny
matrices as well. Against: the thread itself is short, old (2017), drew
only 2 reactions, and the win in the one measured case is ~2.8x, modest by
this corpus's standards. eric-wieser's extension to sum/add.reduce widens
the applicable surface considerably.
