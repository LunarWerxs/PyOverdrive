# OPP-000012: np.isclose wrapper/call overhead

Source: numpy/numpy#16160, "np.isclose is slow", opened by Hoiy on 2020-05-05,
closed 2024-06-22. Labels: `01 - Enhancement`. State at ingestion: closed.

## What is slow

`np.isclose(a, b, rtol=, atol=)` carries meaningfully more overhead per call
than a hand-written equivalent. The original report compared
`np.isclose(0.5, 0, atol=1e-4)` to `math.isclose(0.5, 0, abs_tol=1e-4)` over
10000 iterations: 0.4876s vs 0.0079s, about 61.8x. Once the thread narrowed
to a fair array-vs-array comparison, Hoiy measured `np.isclose(a, b,
atol=1e-4)` on two 1000-element float64 arrays at 38.7 microseconds against
3.36 microseconds for `np.abs(a-b) <= 1e-4` (about 11.5x). Retesting on
NumPy 2.0 in 2024, the apples-to-apples gap (matching rtol+atol) had
narrowed to 20.7 microseconds vs 7.87 microseconds, about 2.63x, per Hoiy's
own arithmetic in the thread.

## Why (per the thread)

Profiling by Hoiy pinned the overhead on the wrapper machinery inside
`isclose`, not the core comparison: repeated `asanyarray` conversions of
`a`, `b`, `atol`, `rtol`; an `np.errstate(invalid='ignore')` context manager
around the tolerance comparison; and two separate `np.all(np.isfinite(...))`
reductions to detect non-finite inputs. Hoiy's `%%prun` profile showed
`np.all` alone consuming about 25% of total runtime, and proposed folding
`np.all(fa) and np.all(fb)` into `np.all(fa & fb)` for roughly a 12%
reduction. seberg separately noted `extobj`/kwargs-vs-vectorcall overhead as
a contributor to function-call cost in this area.

## Who reported and when

Hoiy, 2020-05-05. Active discussion with maintainers rossbar, eric-wieser,
seberg, and WarrenWeckesser ran through 2020-05-10, then Hoiy returned on
2024-06-22 with a retest on NumPy 2.0; the issue was closed the same day.

## Maintainer objections

rossbar, 2020-05-05: "NumPy functions are intended to be run on NumPy
arrays - in this case, you are passing in scalar values which are converted
to arrays under-the-hood by `np.isclose`. This (along with some other
additional setup) incurs some overhead which is likely what makes
`np.isclose` slower than `math.isclose` for scalar inputs." This directly
challenges the framing of the original 61.8x number: it is a scalar-path
comparison against a different stdlib function, not a numpy-internal
inefficiency in the array case.

seberg, 2020-05-10: "I think we will accept PRs for some of the things you
found, but there is probably only so much to be done, considering that this
calls many functions all of which incur a significant overhead since they
are written to be fast for arrays and not scalars. (and in general any
function call has a fairly significant overhead)." seberg returned in 2024
to note "errstate is *much* faster in NumPy 2.0 (although it may be possible
to optimize it even more now)", which lines up with Hoiy's improved 2024
numbers.

## Existing projects / PRs that attempted it

- **numpy/numpy#26252**, "ENH, BENCH: isclose runs faster by using errstate
  only when needed" (closed): a numpy-internal PR, listed in this issue's
  cross-references, that appears to address exactly the errstate overhead
  Hoiy and eric-wieser discussed.
- No sortednp-style third-party reimplementation is named in this thread;
  the alternative pointed to throughout is `math.isclose` (stdlib, scalar
  only) or hand-rolled numpy expressions using `np.abs`/`np.less_equal`
  directly.

## PRs that attempted it

Cross-referenced from the issue's timeline, beyond numpy/numpy#26252 above:
several downstream projects worked around the slowness rather than fixing
numpy itself, e.g. `py-pdf/pypdf_table_extraction#166`, titled "[REF] slow
np.isclose to math.isclose", and `#94` referencing a related camelot issue;
`Qiskit/qiskit#5915` and `qcc4cp/qcc#16` also cross-reference this issue in
performance-tuning PRs; `fjosw/pyerrors#10` likewise. None of these change
numpy itself; they are evidence that the overhead was felt widely enough for
other projects to route around `np.isclose` in hot paths.

## What semantics differ

None, if implemented carefully: this is a call-overhead reduction, not an
algorithm change, so output values should be unchanged. The one sharp edge
WarrenWeckesser raised (2020-05-09): the `errstate(invalid='ignore')` guard
around the tolerance comparison exists for the case where `atol`/`rtol`
themselves are non-finite (his example: `atol=np.inf`, `rtol=-np.inf`),
which he called "a bit extreme" but did not rule out. A fast path that drops
`errstate` unconditionally would let a `RuntimeWarning` leak through in that
edge case where stock `isclose` currently suppresses it silently - a real,
if narrow, behavioral difference.

## Is it common enough to matter

The overhead here is a fixed per-call cost (microseconds), so it matters
most for scalar or small-array `isclose` calls made repeatedly in a loop,
exactly the case seberg generalized as "any function call has a fairly
significant overhead" in NumPy. It is proportionally negligible for large
arrays, where elementwise arithmetic dominates the fixed wrapper cost; the
thread never benchmarks beyond 1000 elements, so there is no evidence either
way for large-N regimes. This is the same shape as OPP-000005 (call
overhead) rather than a novel algorithmic opportunity.

## What PyOverdrive should do next

1. Write the Dyno reproducer: baseline `np.isclose(a, b, rtol=1e-05,
   atol=1e-08)` against a candidate fused-predicate implementation that
   skips the redundant `asanyarray`/`errstate`/double-`np.all` wrapper path,
   swept over `dtype in {float32, float64}`, `size in {1, 10, 100, 1000,
   10000, 100000}`, and both the scalar-pair case (`a=0.5, b=0`, matching
   the original report) and the array-pair case (random arrays via
   `np.random.default_rng()`, matching Hoiy's 2020/2024 microbenchmarks).
2. If the fused-predicate candidate reproduces a speedup concentrated at
   small sizes and decaying toward parity at large sizes, that confirms the
   call-overhead diagnosis and argues for routing through OPP-000005's
   general call-overhead mechanism rather than an `isclose`-specific patch.
3. Before shipping, add a differential-correctness sweep specifically for
   non-finite `atol`/`rtol` values (`inf`, `-inf`, `nan`) and for NaN/Inf
   entries in `a`/`b`, since that is the one place WarrenWeckesser flagged a
   real (if extreme) semantic dependency on the `errstate` guard.
4. Check numpy/numpy#26252's merged diff against current main before
   building anything: if it already ships the errstate-only-when-needed
   fix, PyOverdrive's opportunity may already be partially closed upstream,
   and the reproducer should benchmark against current main, not just the
   2024 numbers quoted in this issue.

## Does it reproduce (2026-08-23, fp 8f8198d9abab, numpy 2.4.5, contended box)

The fused predicate wins clearly at the regime the claim targets: scalar_pair
2.78x (8399.9 ns -> 3019.9 ns), float64 n=1 2.55x, n=10 2.48x, float32 n=10
2.46x, n=1 2.27x - matching or beating the claimed 2.63x. The win decays as
input_regime predicted: float64 n=1000/10000/100000 drop to 1.84x/1.29x/1.25x,
float32 to 1.96x/1.64x/1.08x (near parity at 1e5). It is not a free lunch:
edge_rtol_neg_inf loses at 0.90x and edge_nan_inf_entries_default_tol loses
at 0.83x, while edge_atol_inf is roughly parity (1.01x). All 18 cases report
correct=true. Run was contended (35-43% foreign CPU load), so treat absolute
ns as noisy, not the relative ranking.

A transparent PyOverdrive fast path looks worth shipping, gated to the regime
that actually wins: scalar or small-array (n up to a few hundred) float32/
float64 inputs with finite non-array rtol/atol and equal_nan=False, falling
back to stock isclose above that size and on the two edge cases where the
fused predicate measurably loses.
