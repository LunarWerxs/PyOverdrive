# OPP-000008: threaded chunked dispatch for ufuncs

## What is slow

A single NumPy ufunc call runs on one thread, no matter how many CPU cores are available. For a compute-bound elementwise kernel such as `np.sin`, a program pays for one core's worth of throughput while the rest of the machine sits idle, even though the operation is embarrassingly parallel: each output element only depends on the matching input element.

## Why, per the thread

The reporter (mattharrigan) benchmarked `np.sin(x, out=x)` on a 10,000,000-element float64 array against the same call split into 4 contiguous chunks, each submitted to a `ThreadPoolExecutor` running `np.sin(chunk, out=chunk)`. He reported roughly a 3x reduction in wall time on a 4-physical-core machine. His reasoning: NumPy's C loops for transcendental functions like `sin` release the GIL while they run, so Python threads can run those loops concurrently even though Python bytecode itself cannot. He flagged the caveat that a memory-bandwidth-bound ufunc like addition "probably wont go any faster and might be worse", since bandwidth, not compute, is the bottleneck there.

## Who reported it, and when

Opened by mattharrigan on 2016-10-24 as issue numpy/numpy#8208, "ENH: parallel processing for ufuncs". Closed the same day, within about three hours.

## Maintainer objections

- shoyer: dask.array is a solid existing way to get parallel ufuncs with NumPy and multi-threading; first-class parallel processing support is probably out of scope for NumPy itself.
- rgommers (agreeing): "that's definitely out of scope. We should make it possible (releasing GIL when possible etc.), but we shouldn't add functions like `np.parallel`." Closed the issue citing dask.array, IPython parallel, and joblib.Parallel as existing, sufficient options.

Neither maintainer disputed the reported number or the GIL-release mechanism. The objection is architectural: NumPy should expose the building blocks (GIL-releasing kernels) and leave orchestration to other libraries, not own a parallel-dispatch API itself.

## Existing projects and PRs

No PR against numpy/numpy attempted this feature in the thread; the only cross-reference the crawler surfaced, pygeos/pygeos#2, is unrelated (it replaces a NumPy structured dtype with a Python extension type). Maintainers pointed at three external solutions instead: dask.array (chunked, lazy, multi-threaded/multi-process arrays), IPython parallel, and joblib.Parallel. All three exist today and all add adoption friction: a new array type, a cluster/engine model, or manual chunking, none of which give back `np.sin(x)` unmodified.

## What semantics differ

None for the core computation: chunking `np.sin` over `out=` slices with a thread pool is bit-identical to the single-threaded call, since each output element is independent and inputs are only read. What differs is operational: thread pool creation and chunk bookkeeping add fixed overhead, so there is a break-even size below which threading is a net loss, and the outcome is not uniform across ufuncs. NumPy only releases the GIL above an internal size threshold, and only for compute-bound kernels; this record's `np.add` contrast case exists to make that visible, since addition is bandwidth-bound and should show flat or negative scaling under the same chunking mechanism.

## Is it common enough to matter

Transcendental and other compute-heavy elementwise ufuncs (`sin`, `cos`, `exp`, `log`) on large float arrays are common in scientific Python code, and the issue is a "popular topic" per rgommers' closing comment, with three named alternatives already serving this need. That argues for real demand and against urgency: users needing this today already have dask, joblib, or hand-rolled threading. PyOverdrive's opportunity is offering the same scaling transparently, as a drop-in `np.sin(x)` fast path, without a library swap or explicit chunking code from the caller.

## What PyOverdrive should do next

1. Run the reproducer (`benchmarks/historical/opp_000008_parallel_ufunc.py`) on fingerprinted hardware to verify the claimed scaling holds on current NumPy, and find the break-even size where threading overhead stops paying for itself; that threshold is unmeasured here.
2. Confirm np.add (or another bandwidth-bound ufunc) is flat or negative as predicted; if it scales too, the underlying assumption needs revisiting.
3. If verified, scope a GIL-releasing-ufunc allowlist (starting with `sin`, `cos`, `exp`, `log`, `sqrt`) with a size-gated fast path built on a shared, reusable thread pool created once, not per call.
4. Treat thread count as tunable, not constant: 4/8/16 in the reproducer sweep is a starting grid, and the right default likely depends on core count and array size together.

## Does it reproduce (2026-08-23, fp 8f8198d9abab, numpy 2.4.5)

Yes, and it exceeds the claim. `np.sin` on 1e7 float64: 4 threads 4.30x,
8 threads 6.28x, 16 threads 7.21x against the issue's ~3x on 4 threads. At
1e6 the sweet spot is 8 threads (5.70x); at 1e5 threading is marginal (4
threads 1.49x) and 16 threads LOSES (0.75x), so the crossover on this machine
sits between 1e5 and 1e6 elements. The bandwidth-bound control only half
holds: `np.add` at 1e7 still gains 2.4-2.75x before plateauing at 8 threads,
because one Zen 4 core cannot saturate dual-channel DDR5 on its own.
Evidence: `benchmarks/results/OPP-000008/8f8198d9abab.json`.

Read those as what they are: CANDIDATE-level numbers from the Zen 4
reproducer, which is where the idea was validated. They are not dispatch
thresholds and they are much higher than what the Intel box delivers end to
end - see the calibration bullets below, and note that the two machines
genuinely differ here rather than one of them being mismeasured (Zen 4 is a
uniform CPU, so the P-core/E-core coin flip that corrupted the Intel
calibration does not apply to it).

## Shipped: the `pyrallel_<op>` fast-path family (Phase 4 prototype)

Status: performance_validated. Design record: `docs/decisions/ADR-0002`.

- Core: `src/pyoverdrive/parallel/pyrallel.py`, one persistent
  process-wide pool, created lazily, capped at `min(cpu_count, 16)`,
  overridable with `PYOVERDRIVE_THREADS` (`=1` is the whole-core kill
  switch). Workers only ever run the stock ufunc obtained through
  `Gearbox.stock_fn`, and never wait on other tasks, so deadlock is
  impossible by construction.
- Surface: `np.<op>(x)` and `np.<op>(x, out=o)` for sin, cos, tan, exp,
  log, log10, tanh, sqrt over float64 and float32, C-contiguous plain
  ndarrays only, bit-identical to stock. `isinstance(np.sin, np.ufunc)` is
  the one observable difference while patched; ufunc attributes and methods
  (`.at`, `.reduce`, `.nin`, ...) are mirrored onto the wrapper.
- Calibration, RE-DERIVED 2026-08-24, and the table it replaced was wrong in
  15 of its 16 rows. The original came from the 112-case battery
  `benchmarks/micro/bench_pyrallel_calibration.py` via
  `lab/cli/calibrate_pyrallel.py`, which times the CANDIDATE
  (`parallel_unary`) against the bare ufunc. Neither the candidate-vs-
  dispatched difference nor the blocked-vs-interleaved timing turned out to
  matter - both were measured and both agree. What mattered was that the
  BASELINE is a coin flip on a hybrid CPU: a single-threaded process is
  placed on a P-core or an E-core and stays there, so the same np.sin
  float64 n=1e5 baseline came back 344 us in 15 of 25 fresh processes and
  497 us in the other 10, 1.44x apart. A threaded candidate spans cores and
  averages over the split, so it moves the denominator of every ratio and
  never the numerator - always in our favour. The recorded 1.59x for that
  cell (stock 490.8 us, `pyrallel_4t` 307.8 us, on a box its own conditions
  block calls idle) is a run that drew an E-core; the candidate is unchanged
  today at ~302 us and stock is 344 us, so the honest number is 1.10x.
  Full write-up: `docs/research/hybrid-cpu-baseline-coin-flip.md`.
- The replacement is `tools/calibrate_dispatch.py`: end to end through the
  patched public name, one cell per process, sides interleaved, only on
  processes that drew a fast core, and each threshold is the smallest size
  clearing 1.3x on the WORST of {sorted, shuffled} x {bare, consumed} there
  and at every larger measured size. Evidence:
  `benchmarks/results/PYRALLEL-DISPATCH-CAL/9bbe7063c555-run{1,2}.json`
  (96 + 70 cells; every shipped row cleared the bar on BOTH sweeps, with the
  worse reading kept per cell).
  Resulting table (threshold in elements, worst-case win at threshold, at
  1e7), float64: sin 3e5 1.36x 1.94x; cos 3e5 1.35x 1.88x; tan 1e6 1.31x
  1.90x; exp 3e5 1.41x 2.03x; log 1e6 1.34x 1.82x; log10 1e6 1.41x 1.89x;
  tanh 3e6 1.63x 2.04x. float32: sin 3e6, tan 1e6, log10 1e6, tanh 3e6, and
  cos/exp/log at 1e7. Every row cleared the bar on TWO independent sweeps
  with the worse reading kept per cell, and the second sweep moved no floor.
- `sqrt` is REMOVED from the family, not merely raised: it clears 1.3x at no
  measured size on either dtype (best 1.19x at 1e7 float64), and at its old
  shipped floor of 1e6 float64 it ran at 1.05x. Memory-bandwidth bound, so
  threads have nothing to divide.
- Sorted input is now part of the calibration because it is not a corner
  case here - `np.sin(np.linspace(...))` is close to the canonical call -
  and because it is the harder case in two independent ways. NumPy's own
  trig kernels run ~2.2x FASTER on sorted data (sin at n=1e5: 338 us sorted
  vs 753 us shuffled), leaving threading much less to win back; and because
  PyRallel splits into CONTIGUOUS chunks, sorted input gives each chunk a
  different sub-range of the domain and so unequal work. Measured per chunk
  at n=1e5, 4 chunks, np.tan over [-1.5, 1.5]: 167/58/58/167 us, a 2.9x
  spread that caps the achievable speedup at 2.7x before a thread is
  created; the same values shuffled spread only 1.3x. Rebalancing was
  measured and REJECTED - see the negative result below.
- NEGATIVE RESULT, chunk rebalancing (`tools/probe_chunk_grain.py`). Given
  the 2.9x chunk spread above, the textbook repair is to cut the array into
  more pieces than there are threads. Two forms were measured. OVERSUBSCRIBE
  (one submit per piece, dynamic hand-out) collapses at the sizes that
  matter - at n=1e5 with 4 threads it goes 1.13x, 0.97x, 0.56x, 0.36x, 0.20x
  as the grain rises, because a submit plus a Future costs 5-10 us and the
  whole call is only ~300 us. BLOCK-CYCLIC (same pieces, statically dealt
  round-robin, so the submit count never changes and it needs no lock and no
  GIL-atomicity assumption) is far better behaved and still does not pay:
  across 8 ops x 2 orders at n=3e5 a grain of 2 beat grain 1 in 3 cases and
  lost in 5, and a grain of 4 beat it in 2 and lost in 6. The apparent wins
  sat inside the run-to-run spread. The mechanism is real and the repair is
  not worth it, because the imbalance is worst exactly where stock is also
  fastest, so the absolute time on the table is small next to the per-piece
  overhead. One chunk per thread stays.
- Semantics found and handled while shipping: `np.errstate` is thread-local,
  so chunks on worker threads did not inherit the caller's error mode (a
  caller under `seterr(all="raise")` would have silently not raised). The
  path now mirrors the caller's `geterr()` into every chunk and refuses
  `raise`/`call`/`log` modes (they stay on stock); covered by
  `tests/test_pyrallel.py`. The `out=` form exists because fresh-allocation
  first-touch page faults inside the workers measured 25-40% slower than
  writing into a pre-touched buffer at 1e6 float64.
- Deliberately NOT in this prototype (ADR-0002): reductions (chunking
  changes the pairwise summation tree, a numeric contract needing its own
  tolerance policy), binary ufuncs (the `np.add` gain is a bandwidth effect
  and needs a broadcasting-aware predicate), and a measured answer to the
  Phase 4 "no oversubscription catastrophe with BLAS" gate, which is argued
  from the pool's hard cap and the kernels' freedom from BLAS/OpenMP but not
  yet benchmarked against a live OpenBLAS workload.

## Shipped, second batch: the binary family and a cheaper dispatcher

- `pyrallel_add` / `subtract` / `multiply` / `divide` / `maximum` /
  `minimum` (`src/pyoverdrive/fastpaths/parallel_binary.py`) for two
  same-shape, same-dtype, C-contiguous float64 / float32 / int64 operands,
  with or without an exact-match `out=`; no broadcasting, no casting, no
  scalars (all stay on stock).
  `a + b` resolves to `ndarray.__add__` in C and is not reachable by module
  patching; only explicit `np.add(a, b)` calls are accelerated.
- RE-DERIVED 2026-08-24 and most of the table did not survive. The old rows
  came from the 80-case `PYRALLEL-BIN-CAL` battery, which has the same
  coin-flip baseline as its unary twin (a single-threaded process is placed
  on a P-core or an E-core and stays there, 1.44x apart, always inflating a
  threaded candidate). Measured end to end at their 1e6 floors the family
  delivered 1.04-1.20x against a promised 1.3x, and `subtract` float32 at
  its 3e6 floor ran at 0.97x - a dispatched loss that the pessimization
  sweep could not see, because that sweep probes one canonical input per
  path and this path's is float64.
- Its floors are derived from TWO independent sweeps with the worse reading
  kept per cell, which for this family is not pedantry. The wins are
  bandwidth; they cross 1.3x only between 1e7 and 3e7 elements, and the
  run-to-run spread there is as wide as the margin - one sweep read
  `subtract` float64 at 1.23x, 1.14x, 1.33x on consecutive sizes, which is
  non-monotone, so a threshold read off a single sweep is fitting noise.
  Evidence: `benchmarks/results/PYRALLEL-DISPATCH-CAL/9bbe7063c555-binary-run{1,2}.json`.
- What survives: `np.add`, `maximum`, `minimum` on float64/int64 at 2e7,
  `subtract` int64 at 2e7, `multiply` int64 at 1e7 - 1.31-1.38x at the
  floor on the worse reading. Every float32 row is gone (best 1.28x;
  float32 halves the bytes per element, so a given element count carries
  half the bandwidth pressure) and `np.divide` left the family entirely
  (float64 peaks at 1.32x but dips to 1.29x at 2e7, so no size clears the
  bar and stays clear above it). Below ~1e6 threading still LOSES 4-10x,
  which is what the floors prevent.
- This family is the strongest candidate in the project for per-machine
  calibration rather than a shipped table: bandwidth is the least
  transferable number measured here, and the Zen 4 evidence that motivated
  the family (np.add 2.4-2.75x at 1e7) is far above anything Intel shows.
  Doing it needs the calibration probes run in re-drawn subprocesses first,
  since an in-process probe of a THREADED candidate reintroduces the coin
  flip inside the shipped product; `src/pyoverdrive/calibration.py` carries
  that warning.
- Dispatch tax, measured while shipping this family: a patched tiny call
  paid ~950 ns over stock (a 10-element `np.add` went from 460 ns to 1.4 us).
  Gearbox now precompiles a per-op list of enabled paths and runs the loop
  inside the wrapper closure, and every PyRallel predicate checks size
  first; the tax is ~300 ns now (0.5-0.6x at 10 elements, under 1% from
  1e5 up). Still not free, and still the documented cost of the
  module-patching route for tiny-array hot loops.
