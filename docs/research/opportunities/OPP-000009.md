# OPP-000009: poor free-threaded scaling for repeated small-array workloads

Source: numpy/numpy#27786, "BUG: poor multithreaded performance scaling for
small arrays (nogil)", opened by eundersander on 2024-11-18, closed
2024-12-05. Labels: "00 - Bug", "39 - free-threading".

## What is slow

Under a free-threaded (nogil, `PYTHON_GIL=0`) CPython 3.13 build, the same
small-array numpy workload run on many concurrent threads does not scale;
past roughly 8 threads, aggregate throughput (MFLOPS) collapses instead of
holding flat. In the reporter's sweep (array length 100), throughput peaks
around 206 MFLOPS at 8 threads and falls to 3.42 MFLOPS at 2048 threads, an
order-of-magnitude collapse. The same workload in pure Python lists (no
numpy) keeps scaling through the same thread counts, and multiprocess numpy
(separate GIL per process) also scales fine, isolating the defect to numpy's
in-process thread-safety machinery rather than the underlying math.

## Why (per the thread)

The per-worker loop is `x += 0.01` (elementwise) then `x[0] += x.mean() *
0.01` (a reduction). mattip first suspected OpenBLAS threading, but the
reporter ruled that out with `OMP_NUM_THREADS=1` and the collapse persisted.
ngoldbaum then profiled with a flamegraph and traced the bottleneck to a
critical section guarding numpy's ufunc identity/type-resolution cache in
`numpy/_core/src/umath/dispatching.c::promote_and_get_info_and_ufuncimpl`.
Every ufunc call does a lookup against this cache, and under free threading
that lookup is serialized by one lock shared across all threads calling any
ufunc, so per-call latency rises with thread count. The reporter's own
hypothesis: free-threaded CPython has a fast, mostly-lock-free path for its
own biased reference counting (PEP 703), and numpy's dispatch cache had no
equivalent per-thread fast path.

## Who reported and when

eundersander, 2024-11-18. ngoldbaum (numpy free-threading lead) picked it up
the same week and drove the fix; colesbury (CPython free-threading lead) and
seberg (numpy maintainer) joined the design discussion. Closed 2024-12-05.

## Maintainer objections

Design tradeoffs about the fix, not disagreement the bug was real:

- mattip: asked whether OpenBLAS threading was the real cause (ruled out).
- colesbury, on a reader-writer lock: "they don't necessarily scale that
  well... because of contention of the count of the number of readers... not
  part of the public Python C API."
- seberg: "a custom hashmap is just too terrible in a free-threaded world."
- ngoldbaum: cache misses leave "almost certain" races inside
  `promote_and_get_ufuncimpl` beyond the hashmap itself, so the fix had to
  cover more than the lookup alone.

## Existing projects / PRs that attempted it

- numpy/numpy#27859, "PERF: add a fast path to ufunc type resolution".
- numpy/numpy#27896 and #27913, both "PERF: improve multithreaded ufunc
  scaling" (second and third passes, referenced as the issue closed).
- numpy/numpy#28577 and #28583, "BUG: avoid deadlocks with C++ shared mutex
  in dispatch cache": the chosen fix used a C++ shared mutex for the
  dispatch cache, which then had its own deadlock bugs needing follow-ups.
- python-pillow/Pillow#8714, "Reduce memory arena contention": cross-linked
  as the same failure shape (a shared cache serialized by one lock under
  nogil) recurring in a different C-extension project, not a numpy fix.

## What semantics differ / is it common enough to matter

No semantic difference: a pure performance bug in numpy's internal ufunc
dispatch, not a change to any public API or numerical result. Relevance is
gated on adoption: free-threaded CPython is still an opt-in, experimental
build (PEP 703, since 3.13), so the pattern is broad in principle (any code
calling numpy ufuncs from many threads on small arrays) but narrow today.
As free-threaded builds mainstream, the underlying bug class (lock
contention on a shared, per-object-type dispatch cache) is likely to recur.

## What PyOverdrive should do next

1. Treat as closed and fixed upstream, not an open opportunity: the fix
   landed via #27859/#27896/#27913 with deadlock corrections in
   #28577/#28583, merged within about two months. Confirm which numpy
   release first carried the full fix set before assuming a version in
   current use is unaffected.
2. Do not build a reproducer here: it requires a free-threaded 3.13t/3.14t
   build (`PYTHON_GIL=0`); this workstation runs standard GIL CPython
   3.14.2, so the contended path is unreachable.
3. If PyOverdrive ever targets free-threaded CPython, revisit this shape (a
   shared, lock-serialized per-type dispatch cache) as a pattern to audit
   in PyOverdrive's own dispatch layer, since an adaptive dispatcher that
   also caches "which kernel to run" per call can reproduce the same
   mistake.
