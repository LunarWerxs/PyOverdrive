# OPP-000021: memory-efficient np.cov for n_samples >> n_features

Source: numpy/numpy#31292, "ENH: memory-efficient `np.cov` for `n_samples >>
n_features`", opened by bruAristimunha on 2026-04-21. State at ingestion:
open, no labels, retrieved 2026-08-23.

## What is slow

`np.cov` centers its input by allocating `m - mean(m)`, a copy the full size
of `m`. When observations vastly outnumber variables (`n_samples >>
n_features`), that centered copy dominates both peak memory and wall time,
even though the resulting covariance matrix itself is tiny. The reporter
proposes an opt-in keyword that instead uses the algebraically equivalent
post-hoc formula `cov = (m @ m.conj().T) / fact - (N / fact) * avg @
avg.conj().T`, which avoids materializing the centered copy and instead pairs
with BLAS `gemm`/`syrk` on the raw data.

## Why (per the thread)

The formula is already implemented in scikit-learn's
`PCA(svd_solver="covariance_eigh")` and the reporter, with scikit-learn
maintainer Olivier Grisel cc'd, wants it upstreamed into `np.cov` itself
rather than reimplemented downstream. On a `(16, 5_000_000)` float64 input
the reporter measured `np.cov(m)` at 136 ms with 640 MB peak allocation
versus the post-hoc path at 69 ms with ~0 MB peak allocation, a 1.97x
wall-clock improvement and, more strikingly, near-total elimination of the
extra allocation. The reporter frames the memory relief as the real prize:
it "opens up matrix sizes that don't fit today," where the centering copy is
the blocker, not the matmul itself. The maximum absolute deviation from
stock `np.cov` on their benchmark was ~2e-14.

## Maintainer objections

betatim, 2026-05-08: "Did you run your experiments regarding the precision
using `float32` as well? I did a few experiments (and asked AI to do some)

In an ideal universe we'd find a way to not introduce a new argument for
`np.cov()`. I'm wondering if there is a way to figure out cases for which we
could always use the post-hoc centering method. So far I have no ideas :("

Neither objection is a rejection. seberg's concern is API-surface bloat
(another `method=` string) more than the algorithm; betatim's concern is
specifically float32 precision and a preference for automatic dispatch over
a manual flag.

## Existing projects / PRs that attempted it

- **scikit-learn's `PCA(svd_solver="covariance_eigh")`**: the reference
  implementation, `C = X.T @ X - N * mean mean.T; C /= (N - 1)`, cited
  directly from `sklearn/decomposition/_pca.py`.
- **scikit-learn#33573** ("FEA Make `LedoitWolf` estimator array API
  compatible", closed) asked for the same trick to move upstream into numpy;
  cited as the motivating cross-reference.
- **numpy PR #6403** (merged 2015) already halved `np.cov` memory once; the
  `m - mean(m)` copy is what remains after that earlier fix.
- **numpy issue #13199** (open) tracks the same memory/precision class of
  problem for `np.var`/`np.std`.
- **numpy issue #6231** proposes Welford's algorithm for the same general
  area but is explicitly called out as orthogonal: "that's orthogonal,
  because post-hoc pairs with BLAS `gemm`/`syrk` and Welford does not."
- Cross-referenced but not attempts at this exact feature:
  WarrenWeckesser/ufunclab#12 (two-pass mean-variance/covariance gufuncs,
  open) and data-apis/array-api-extra#690 (cov correction/weights
  parameters, closed).
- No numpy-internal PR has been opened for this issue itself as of
  retrieval; the reporter offered to draft one but had not by 2026-06-04.

## What semantics differ

The post-hoc formula loses precision when `|avg|^2 / var(m)` is large
(Chan, Golub, LeVeque 1983). The reporter quantifies this precisely:
relative error grows quadratically with the mean-to-standard-deviation
ratio (mu/sigma), matching the Chan-Golub-LeVeque kappa^2 ~= 1 +
(mu/sigma)^2 bound. float32 is safe to about mu/sigma = 10 and degrades
badly by about mu/sigma = 1000; float64 is safe to about mu/sigma = 1e4 and
crosses 1% relative error around mu/sigma = 1e6. The default numpy behavior
would stay the current safe two-pass centered computation; the fast path
activates only if a caller explicitly opts in, and on ill-conditioned data
it returns a numerically degraded but not obviously wrong result, with no
error raised.

## Is it common enough to matter

Plausibly yes, but for a specific and named beneficiary rather than generic
array code: PCA and other covariance-heavy workflows on tall, well-scaled
data, where scikit-learn is already using this exact trick in production.
The reporter also traced pandas' own covariance history: pandas moved from
two-pass centered (2012) to Welford (2020, PR #37453) for stability, tried a
precomputed-means-plus-centered-cross optimization (2021, PR #42761), then
reverted it (2022, PR #45646) after it broke `scipy.spatial.distance.
squareform` by producing a `1 + 4.4e-16` diagonal instead of exactly `1.0`.
Pandas never used the post-hoc form the reporter is proposing here, so this
is not a precedent for the post-hoc trick specifically, but it is a
precedent for how easily a "faster but imprecise" covariance shortcut can
break a downstream consumer that assumes exactness.

## What PyOverdrive should do next

1. Write the Dyno reproducer: baseline `numpy.cov(m)` (stock, no keywords)
   versus a candidate post-hoc implementation `(m @ m.conj().T) / fact -
   (N / fact) * np.outer(avg, avg.conj())`, on 2-D arrays of shape
   `(n_features, n_samples)` with `n_features` in `{2, 16, 64}` and
   `n_samples` swept across `{10000, 100000, 1000000, 5000000}`, dtypes
   `float32` and `float64`, both well-conditioned data (mean near 0,
   unit variance) and deliberately ill-conditioned data (large mean,
   small variance, sweeping mu/sigma through the reporter's claimed
   float32 (~10) and float64 (~1e4) safety thresholds) to check both the
   speed/memory numbers and the precision cliff independently.
2. If the timing and peak-memory numbers reproduce anywhere near the
   reported 1.97x / 640 MB -> ~0 MB on this hardware, measure the actual
   cost of the reporter's proposed auto-detect probe (`max((mu/sigma)^2)`
   in one pass) against the centering cost it would replace, since the
   reporter's own claim that this check costs "roughly half" of centering
   is the deciding fact for whether PyOverdrive can route transparently
   or must stay an explicit opt-in like the reporter's `method=` proposal.
3. If transparent auto-routing clears step 2, prototype the conditioning
   probe plus dispatch as a PyOverdrive fast path for `numpy.cov` on plain
   float64 2-D inputs, falling back to stock for float32 (per betatim's
   flagged extra sensitivity there) and for any input the probe flags as
   ill-conditioned.
4. Differential-test the candidate against stock `np.cov` across the same
   dtype/shape/conditioning grid as step 1, checking both bit-for-bit
   agreement on well-conditioned inputs (reporter's own bound: ~2e-14 max
   absolute deviation) and that the ill-conditioned fallback path is never
   silently skipped.
5. Track this against `assume_unique`/`method=` as existing numpy
   precedents for "trust me, it's already X" opt-in flags (`np.linalg.
   pinv(hermitian=True)`, `np.quantile(method=...)`, cited in-thread), so
   any PyOverdrive-side API choice stays consistent with how numpy itself
   has framed this tradeoff rather than inventing a new convention.

## Does it reproduce (2026-08-23, fp 8f8198d9abab, numpy 2.4.5, contended box)

Ran the full 18-case well-conditioned sweep (n_features 2/16/64, n_samples
10k/100k/1M, float32/float64) against the post-hoc covariance candidate.
All 18 correct, zero losses. Best win: n16_m10000_float32 at 4.69x
(760.4us -> 162.0us); several mid-size float32/small-n64 cases land 2.6x-3.8x,
comfortably past the 1.97x claim. Worst: n2_m1000000_float64 at 1.15x
(8.60ms -> 7.46ms); the case closest to the claim's own (16, 5,000,000)
float64 shape, n16_m1000000_float64, only manages 1.33x (96.1ms -> 72.4ms),
below the claim. Pattern: float64 gains shrink toward 1.0x as n_samples
grows while float32 holds 2.1x-4.7x across the same sweep, so the win is
real but dtype- and shape-dependent, not a flat 1.97x. This battery only
covered well-conditioned data; the mu/sigma precision falloff the thread
itself flags was not probed. A transparent PyOverdrive fast path looks
worth shipping, but only under a predicate that checks dtype (favor
float32, or float64 at moderate n_samples) and a cheap conditioning probe
before routing, exactly the auto-detect gate the opportunity notes already
call out as unverified against its own cost claim.
